How it works

The server renders the current list into the page — the count and the rows are real HTML before any script runs. The browser then hydrates that markup with signal, computed and effect from @basenative/runtime: the filter, the summary line and the counts are derived values, and the server-rendered list stays in sync through the same signal.

On the dev server the app talks to /api/tasks — POST to add, DELETE to remove — the site's one API. The static build has no API, so there the list is kept in your browser's localStorage instead; the notice under the title says so when that is the case.

The pieces are the catalog's own: the server-rendered list is the list group, each status rides as a badge, and the actions are native buttons.

Design axioms

  1. No namespace theater

    Components are built on W3C primitives. No app-button, no my-dialog. A button is a <button>.

  2. Zero inline styles

    All CSS lives in the component's own sheet. No style="", no CSS-in-JS, no classes. A component is addressed by its element and its variant attribute — that is the whole selector contract.

  3. Tokens, all the way down

    Every sheet opens with a :root block mapping the design system's roles onto the component's own tokens. Change a role and every component follows — no component hard-codes a color, a size, or a radius.

  4. One component, three files

    index.html holds structure and bindings, styles.css holds tokens and selectors, index.js holds the view model. Templates carry no literal text; state is carried by ARIA, never by a hook attribute.
