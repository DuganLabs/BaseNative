## What the user hits

A visitor scrolls a long way down `/showcase` to the Pagination section, clicks "2" to see
what happens, and gets thrown back to the top of the same very long gallery. The page reloads
in full, shows identical content, and they have lost their scroll position — so the only way
to get back to the pagination demo is to scroll down again. Every one of the eight controls
does this.

## Why it happens

The showcase passes a real `baseUrl`, so the component renders real navigations, and nothing
on the page intercepts them.

`examples/express/showcase-data.js:660`:

```js
html: renderPagination({ currentPage: 3, totalPages: 10, baseUrl: '/showcase' }),
```

Rendering that call produces eight anchors and one ellipsis span (the original audit said
nine anchors; it is eight):

```
/showcase?page=2 (prev) · 1 · 2 · 3 (aria-current, links to itself) · 4 · 5 · … · 10 · /showcase?page=4 (next)
```

Cloudflare Pages serves `dist/showcase/index.html` for any query string on `/showcase`, so
`?page=2` returns byte-identical HTML. The result is a full document navigation to the same
document — the browser discards the scroll offset and starts at the top.

Nothing intercepts the clicks. `grep -n 'pagination\|data-page' examples/express/public/showcase.js`
exits 1, and the script's only `preventDefault()` calls are in the tabs, dialog and drawer
handlers (`examples/express/public/showcase.js:46`, `:51`, `:56`, `:60`, `:81`, `:237`,
`:243`, `:249`).

Note the component-page demo already does this correctly: `examples/express/component-demo-scripts.js`'s
`pagination:` block uses `href="#p"` with `data-page="N"` attributes and takes over the clicks
itself, so `/components/pagination` does not have this bug. Only `/showcase` does.

## The fix

1. **Change the demo's `baseUrl` to `'#'`** at `examples/express/showcase-data.js:660`:
   `renderPagination({ currentPage: 3, totalPages: 10, baseUrl: '#' })`. Leave the
   accompanying `code:` string at `examples/express/showcase-data.js:661` showing
   `baseUrl: '/items'` — that is the honest illustration of real usage, and it is a code
   sample, not a live link.
2. **Add a click handler to `examples/express/public/showcase.js`** that intercepts anchors
   inside `[data-bn="pagination"]`, calls `preventDefault()`, and re-renders the pager with
   the new current page — the same shape as the block in
   `examples/express/component-demo-scripts.js`. Wire it in the same place the other
   `wire*()` functions are called.
3. Do steps 1 and 2 together, not either alone. `baseUrl: '#'` on its own stops the reload but
   leaves eight dead controls and adds a `#` to the URL; the handler on its own still lets a
   missed selector navigate. Prefer this over dropping the `href`s entirely: an `<a>` without
   `href` is not focusable or keyboard-activatable, which would trade a scroll annoyance for
   an accessibility regression on a page that is otherwise clean.
4. While in `showcase.js`, check whether `/showcase`'s other interactive demos have the same
   gap — the file wires tabs, dialogs and drawers, so confirm nothing else on the page renders
   a live `href` into a demo.

## How we will know it worked

The render is pure, so assert on it. Add to `tests/integration/integration.test.js`, next to
`§ 12. /compare: published claims match the source`
(`tests/integration/integration.test.js:331`) — this fails today:

```js
// no demo on /showcase may render a navigation to a real site route
import { getShowcaseSections } from '../../examples/express/showcase-data.js';
const all = JSON.stringify(getShowcaseSections());
assert.doesNotMatch(all, /href="\/showcase\?/,
  'a /showcase demo links to a real route — Cloudflare Pages ignores the query string and the click reloads the page');
```

`getShowcaseSections()` is the export at `examples/express/showcase-data.js:339`; the
assertion runs over the rendered `html` strings it builds.

The interception itself is DOM behaviour and needs Playwright. `tests/e2e/smoke.spec.js`
exists and `@playwright/test` is a devDependency — add a case: go to `/showcase`, scroll the
pagination demo into view, record `window.scrollY`, click the "2" control, and assert
`window.scrollY` is unchanged and the active page moved. That fails today for both reasons.

## Notes

- BN-036 is the other pagination defect on the site — the component-page demo hand-writes an
  `<ol>` that the `ul`-scoped layout rules miss. Different file, different mechanism. Worth
  reading `packages/components/src/pagination.js` once if both are being worked, but neither
  blocks the other, and this ticket needs no change to the package.
- **Do not "fix" this in the component.** `renderPagination` emitting real `href`s from
  `baseUrl` is correct and is what a consumer building a real paginated list wants. The defect
  is the demo passing a live route as `baseUrl`.
- The reason this is invisible in local development: `pnpm start` runs the Express server,
  which also serves the same page for `?page=2` — so the behaviour is identical locally and
  in production. It is not a Cloudflare-specific bug; Pages is just where users meet it.
  Per the Cloudflare edge-injection memory note, verify the final behaviour in a browser
  rather than with curl.
- `currentPage: 3` means the "3" control links to itself (`aria-current="page"` plus a live
  `href`), which is the most confusing single click on the page. `baseUrl: '#'` fixes that
  too.
