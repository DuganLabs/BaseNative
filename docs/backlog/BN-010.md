## What the user hits

Any calendar event that does not start exactly on the hour — a job booked at 09:30, 10:15, 14:45 — stops being a block in its time slot and instead paints as a single panel covering that whole day column, top to bottom. Because it is the last absolutely positioned child in the column, it also swallows every click and drag that should have landed on the hours underneath it, so the rest of that day becomes unusable: you cannot drag another job onto it, and you cannot click through to anything behind it. On-the-hour events look fine, which is why this survives a casual look at a demo.

## Why it happens

`packages/components/src/calendar.js:266` computes the event's grid row from a *fractional* hour:

```js
const topRow = Math.max(from - hourStart + 2, 2);
```

`from` is fractional by construction — `packages/components/src/calendar.js:85` returns `hour: d.getHours() + d.getMinutes() / 60`. That value is interpolated straight into the inline style at `packages/components/src/calendar.js:273`:

```js
style="grid-row: ${topRow} / span ${rows};${colorStyle}"
```

A 09:30 start on the shipped 7–19 grid therefore emits `grid-row: 4.5 / span 2`. `grid-row-start` accepts an `<integer>`, so the whole `grid-row` declaration is invalid and the parser drops it; the `--bn-calendar-event-color` declaration next to it is a separate declaration and survives, which is why the block still gets its accent colour while losing its position.

With no grid placement left, the block keeps `position: absolute` (`packages/components/src/components.css:1540-1541`) inside the day column, which is `position: relative` and is itself the grid container (`packages/components/src/components.css:1524-1526`). Per CSS Grid §9, an absolutely positioned grid child with no definite grid position resolves its containing block to the grid container's padding box — the entire column. Combined with `inset-inline: var(--bn-space-1); inset-block: var(--bn-space-half)` (`components.css:1542-1543`) and `z-index: 1` (`components.css:1557`) it paints over the full day and intercepts pointer events for every slot and event beneath it.

Only the *span* half of this was hardened: `calendar.js:267-268` already does `Math.max(to - from, 0.5)` then `Math.ceil`, so `span 0` can no longer be emitted. The fractional **start** was never fixed.

The defect is currently pinned as correct by two tests:

- `packages/components/src/components.test.js:2235` — `assert.ok(monday.includes('grid-row: 25.5 / span 1'))`
- `packages/components/src/components.test.js:2518` — `` assert.ok(col.includes(`grid-row: ${start.getHours() + start.getMinutes() / 60 + 2} / span 1`)) ``

Real consumer: `/home/dugan/Developer/github.com/DuganLabs/GreenPut/apps/platform/src/routes/jobs/jobs.ts:525` calls `renderCalendar` with API timestamps that carry minutes and passes no `hours`, so every GreenPut job not booked on the hour hits this.

## The fix

Chosen approach: keep grid placement but make the row integers, and carry the sub-hour remainder as two custom properties the stylesheet turns into an inset offset. This preserves minute-level fidelity (which is the whole point for GreenPut bookings), keeps events aligned to the same rows as slots and labels, and keeps the existing multi-day `continues` segment logic untouched — unlike the alternative of positioning events by percentage of the column, which would delete every grid-row assertion in the suite for no extra accuracy.

1. In `renderCalendar`, `packages/components/src/calendar.js`, replace lines 266-268 with a clamped, integer-row computation:

   ```js
   const clampedFrom = Math.min(Math.max(from, hourStart), hourEnd);
   const clampedTo = Math.min(Math.max(to, clampedFrom + 0.5), hourEnd);
   const startOffset = clampedFrom - hourStart;          // hours below the top of the grid
   const endOffset = clampedTo - hourStart;
   const firstRow = Math.floor(startOffset);             // 0-based
   const lastRow = Math.max(Math.ceil(endOffset), firstRow + 1); // exclusive
   const rows = lastRow - firstRow;
   const topRow = firstRow + 1;                          // subgrid-local; see BN-063
   const lead = startOffset - firstRow;                  // 0..1 trimmed off the top
   const trail = lastRow - endOffset;                    // 0..1 trimmed off the bottom
   ```

   Note `topRow` is `firstRow + 1`, not `+ 2` — that is BN-063's correction, and these are the same three expressions BN-063 touches, so land both in one change.

2. Still in the event template at `calendar.js:273`, emit the offsets only when they are non-zero, so on-the-hour events keep their current style string:

   ```js
   const offsetStyle =
     lead > 0 || trail > 0
       ? ` --bn-calendar-event-rows: ${rows}; --bn-calendar-event-lead: ${lead}; --bn-calendar-event-trail: ${trail};`
       : '';
   ```

   and append `${offsetStyle}` after `${colorStyle}` inside the `style` attribute.

3. In `packages/components/src/components.css`, replace the `inset-block: var(--bn-space-half);` shorthand at line 1543 with the two longhands that consume those properties:

   ```css
   inset-block-start: calc(var(--bn-space-half) + (var(--bn-calendar-event-lead, 0) / var(--bn-calendar-event-rows, 1)) * 100%);
   inset-block-end: calc(var(--bn-space-half) + (var(--bn-calendar-event-trail, 0) / var(--bn-calendar-event-rows, 1)) * 100%);
   ```

   The containing block is the event's grid area (`rows` tracks tall), so one hour is `100% / rows`; the fallbacks reproduce today's behaviour exactly for on-the-hour events.

4. Update `docs/api/components.md:985`, which shows a sample event as `style="grid-row: 4 / span 2;"`, to the new numbering.

## How we will know it worked

Add to the `renderCalendar` describe block in `packages/components/src/components.test.js` (next to the existing row-alignment test at `components.test.js:955-972`):

```js
it('places a half-past event on an integer row with a sub-hour offset', () => {
  const html = renderCalendar({
    startDate: '2025-06-02',
    hours: { start: 7, end: 19 },
    events: [{ id: 'h', title: 'Half past', start: '2025-06-02T09:30', end: '2025-06-02T10:30' }],
  });
  const style = html.match(/data-event-id="h"[^>]*style="([^"]*)"/)[1];
  assert.match(style, /grid-row: 3 \/ span 2/);
  assert.ok(!/grid-row: \d+\.\d/.test(style), 'grid-row start must be an integer');
  assert.match(style, /--bn-calendar-event-lead: 0\.5/);
});
```

Before the change this fails on the first assertion (it emits `grid-row: 4.5 / span 2`); after, it passes. Run it with `cd packages/components && node --test` (the repo uses the Node built-in runner — CLAUDE.md §"All packages use Node.js built-in test runner (`node:test`). No Jest, no Vitest").

The existing assertions that currently pin the bug must be recomputed with the new formula; they are at `components.test.js` lines **2235, 2245, 2518, 2525, 2530, 2563, 2618, 2637, 2655, 2656, 2657, 2666, 2675**. (Line 2483 also contains `grid-row` but belongs to `renderLayoutGrid` — leave it alone.) Worked example for line 2235: hours `{start: 0, end: 24}`, event `23:30–00:30` clips to `23.5–24`, giving `firstRow 23`, `lastRow 24`, so `grid-row: 24 / span 1` with `--bn-calendar-event-lead: 0.5`.

Also worth one manual check that no test can make: open `/components/calendar` on the example site with a half-hour event and confirm the block sits half a row down and the slots beneath it are still clickable — the "covers the whole column" symptom is a layout fact, not a string fact.

## Notes

- **Shares a root cause with BN-063.** BN-063 fixes the `+2` → `+1` off-by-one on all three emissions (labels `calendar.js:259`, slots `calendar.js:284`, events `calendar.js:266`) caused by those children living in a subgrid, not the outer grid. This ticket rewrites the event expression anyway, so do BN-010 and BN-063 as one change and update the row numbers in the test suite once. BN-063 is marked `depends_on: [BN-010]` for exactly that reason.
- The comment block at `calendar.js:250-254` argues *for* the `+2` convention. It is wrong (see BN-063) and must be rewritten in the same commit, or the next reader will restore the bug.
- Do not "fix" this by rounding `from` to the nearest hour. That silently relocates a GreenPut booking by up to 30 minutes on a screen a dispatcher reads as authoritative.
- CLAUDE.md axiom 2 is "Zero inline styles". The calendar already violates the letter of it for grid geometry (as does `renderLayoutGrid`, see `docs/api/components.md:1164`) because per-event geometry cannot live in a static stylesheet. Step 2 keeps the violation as small as it already is — values only, in custom properties, with the actual rules in `components.css`. Do not move the `calc()` inline.
