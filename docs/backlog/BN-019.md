## What the user hits

Open a drawer and it slides in, but nothing inside it responds: the × in its header cannot be clicked, cannot be tabbed to, and is invisible to a screen reader. No dimmed backdrop appears behind it either, so clicking outside does not dismiss it, and Escape does nothing. The drawer is a dead panel you cannot close. On a 390px phone the 20rem panel covers the viewport, so the only way out is to reload the page. Every visitor to `/components/drawer` lands in exactly this state, because the demo renders the drawer closed and the "Open drawer" button puts it into the broken state.

## Why it happens

Three separate holes, all in the same handoff between the renderer and a client that does not exist.

**1. `inert` is applied and never removed.** `packages/components/src/drawer.js:44`:

```js
const stateAttrs = open ? ' data-open' : ' inert';
```

The doc comment at `packages/components/src/drawer.js:11-13` promises "the client removes `inert` when it adds `data-open`". No shipped code does that. `packages/components/src/index.js:68` exports only `renderDrawer` — there is no `initDrawer` anywhere in the package (the package's only client initialisers are `initTabs` at `index.js:71` and `initCalendarDragDrop` / `initPipelineDragDrop` at `index.js:92`). The example site's demo script at `examples/express/component-demo-scripts.js:255-258` sets `drawer.setAttribute('data-open','')` and never touches `inert`. `inert` on the `<aside>` makes its whole subtree non-interactive and hidden from assistive technology, so the close button at `drawer.js:41` receives no click and no focus even though `component-demo-scripts.js:264` registers a listener on it. The CSS transform that slides the panel in (`packages/components/src/components.css:1027`, `[data-bn="drawer"][data-open] { transform: translateX(0); }`) is unaffected by `inert`, which is why it looks open.

**2. The overlay is toggled with the wrong attribute.** `component-demo-scripts.js:257` calls `overlay.removeAttribute('hidden')` and `:261` sets it — but the overlay is rendered without `hidden` in the first place (`packages/components/src/drawer.js:43` emits `<div data-bn="drawer-overlay">` plus `data-open` only when open), and the stylesheet gates the scrim on `data-open`: `packages/components/src/components.css:1030-1043` gives `[data-bn="drawer-overlay"]` `opacity: 0; pointer-events: none` and only `[data-bn="drawer-overlay"][data-open]` gets `opacity: 1; pointer-events: auto`. So no scrim ever paints and the overlay's dismiss listener (`component-demo-scripts.js:263`) can never fire — the element is `pointer-events: none`.

**3. No Escape handler exists on any surface.** There is no `keydown` listener in `drawer.js`, in `index.js`, or in the demo script.

## The fix

Chosen approach: ship the documented client contract as `initDrawer` in the package, rather than dropping `inert` from the renderer. Dropping `inert` would leave a closed, off-screen drawer fully tabbable — a worse accessibility bug than the one being fixed — and every consumer would otherwise have to reimplement the same open/close/Escape/scrim logic. The package already has the precedent (`initTabs`, `initCalendarDragDrop`).

1. Add `initDrawer(drawer, options)` to `packages/components/src/drawer.js`, following the shape `initTabs` uses in `packages/components/src/tabs.js:80` (returns an object with imperative methods plus `destroy()`):
   - `open()` — remove `inert` from the `<aside>`, add `data-open` to it, add `data-open` to the associated overlay, remember `document.activeElement` as the return target, and move focus to the close button (or the panel itself when `closable: false`).
   - `close()` — remove `data-open` from the `<aside>` and the overlay, restore focus to the remembered element, then set `inert` on the `<aside>`. Set `inert` **after** moving focus out, or the focus call is ignored.
   - `toggle()`, and a `destroy()` that removes every listener it added.
   - Listeners: click on `[data-bn="drawer-close"]` within the drawer → `close()`; click on the overlay → `close()` (unless `dismissible: false`); `keydown` on `document` for `Escape` while open → `close()`.
   - Locate the overlay by walking back from the drawer: `drawer.previousElementSibling` when it matches `[data-bn="drawer-overlay"]`, else accept an explicit `options.overlay`. This matters because `renderDrawer` emits the overlay as a *sibling before* the `<aside>` (`drawer.js:46`), not as a parent.
2. Export it from `packages/components/src/index.js` beside `renderDrawer` at line 68: `export { renderDrawer, initDrawer } from './drawer.js';`.
3. Update the doc comment at `packages/components/src/drawer.js:11-13` to name `initDrawer` as the client that removes `inert`, instead of an unnamed "the client".
4. Rewrite the demo script at `examples/express/component-demo-scripts.js:250-265` to call `initDrawer` and drop the `hidden` attribute manipulation entirely. The demo pages load the site bundle; confirm `initDrawer` is reachable there — `grep -o 'init[A-Za-z]*' examples/express/public/basenative.js` currently returns only the substring `initial`, i.e. the bundle ships **no** initialisers today, so the bundle's build input needs the new export added alongside whatever change BN-018 makes there.
5. Add the `initDrawer` row to the client-side section of `docs/api/components.md` (the Drawer entry).

## How we will know it worked

Add a `describe('initDrawer')` block to `packages/components/src/components.test.js` next to the existing drawer tests at `components.test.js:1755-1782`. The package tests are string-level, so drive it against a minimal DOM stub in the same style the calendar's `initCalendarDragDrop` tests use (search the file for `initCalendarDragDrop` for the stub pattern already in the repo). The assertion that fails before and passes after:

```js
it('removes inert when it opens and restores it when it closes', () => {
  // render closed, initDrawer(...).open()
  assert.ok(!drawerEl.hasAttribute('inert'), 'an open drawer must not be inert');
  assert.ok(overlayEl.hasAttribute('data-open'), 'the scrim must be shown by data-open, not hidden');
  // .close()
  assert.ok(drawerEl.hasAttribute('inert'));
  assert.ok(!overlayEl.hasAttribute('data-open'));
});
```

Before the change the test cannot even be written — `initDrawer` does not exist — which is itself the signal. Keep the existing `components.test.js:1755-1765` assertions (closed renders `inert`, open renders without it) unchanged; the renderer's contract is not changing.

Two things to check by hand, because no test in this repo runs a browser: on `/components/drawer`, (a) open the drawer and click the ×, then press Escape on a second open — both must close it; (b) with the drawer closed, press Tab repeatedly and confirm focus never enters the off-screen panel.

## Notes

- Related to **BN-018**, which asks the broader question of whether `@basenative/components` ships interaction at all. This ticket answers it for the drawer specifically and is marked `decision_needed: false` because the renderer *already committed* to a client contract in its own doc comment at `drawer.js:11-13` and in the `inert` it emits — the markup is unusable without one, so there is no markup-only option here. If BN-018 is resolved toward "markup only", `initDrawer` is still the right fix for this one; the alternative would be removing `inert`, which is a regression.
- Do not reach for `<dialog>`/`showModal()` or the Popover API to get dismissal for free. The drawer is `position: fixed` with a slide transform (`components.css:1008-1027`) and its own scrim element; moving it to the top layer changes its stacking, its transition, and its `data-bn` contract, and `renderDialog` already exists (`index.js:65`) for the modal case.
- The overlay is a **preceding sibling** of the `<aside>`, not a wrapper (`drawer.js:46` returns `${overlayHtml}<aside …>`). Code that assumes `drawer.closest(...)` or `drawer.parentElement.querySelector(...)` will silently find nothing when two drawers are on one page.
- CLAUDE.md: tests are the Node built-in runner (`cd packages/components && node --test`); no Jest, no Vitest. Commits follow Conventional Commits.
