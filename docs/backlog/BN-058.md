## What the user hits

A developer evaluating BaseNative reads `/compare` — the page that sells itself as the
honest look at where the framework loses — and is told three separate times that there is no
hot module replacement: the feature table scores it a cost against React, Vue and Svelte,
"Where others win" lists it, and "Probably not" tells them to go elsewhere if HMR matters to
their workflow. All three are false. `@basenative/hmr` is a published package, and the very
dev server serving them that page has it registered as its first middleware. The page talks a
qualified reader out of the product over a feature that shipped.

## Why it happens

Three hand-written assertions in the view were never revisited after the package landed.

`examples/express/views/compare.html:236-242`:

```html
          <tr>
            <th scope="row">Hot reload</th>
            <td data-tone="cost">Browser refresh</td>
            <td data-tone="win">Fast Refresh</td>
            <td data-tone="win">HMR</td>
            <td data-tone="win">HMR</td>
          </tr>
```

`examples/express/views/compare.html:293`:

```html
        <li>No HMR — manual browser refresh during dev</li>
```

`examples/express/views/compare.html:324`:

```html
        <li>Apps where HMR and devtools are critical workflow</li>
```

Against that: `packages/hmr/package.json` is `@basenative/hmr` at version `0.2.0`,
described as *"Dev-only hot module replacement — state-preserving DOM patching, focus and
caret retention, SSE live reload"*, with 21 files in `packages/hmr/src/`. Its README's first
section heading is *"Why this is HMR and not a live reload"*, and it explains precisely the
distinction the compare table gets backwards — a live reloader calls `location.reload()` and
throws away the caret, the scroll position and the open dialog; this one patches the DOM.

And the site itself uses it. `examples/express/server.js:4`:

```js
import { hmrMiddleware } from '@basenative/hmr';
```

registered at `examples/express/server.js:16-17`, before every other middleware, with the
comment *"Registered first so /__bn_hmr/* wins before the static handlers."*

Why it survived: `/compare` **is** guarded — `checkComparePage()`
(`scripts/check-compare-page.js:37`, called from `scripts/build-pages.js:67` and from
`tests/integration/integration.test.js:335`) refuses to build a page whose numbers disagree
with the source. But that guard only covers `RENDERED_CLAIMS`, the *measured numeric* facts
(runtime size, dependency count, primitive count). Prose claims like "No HMR" are outside
its remit, so the one page in the repo with a truth guard has an unguarded half.

## The fix

Correct the three assertions, then extend the existing guard to the class of claim that
escaped it.

1. **Feature table** — `examples/express/views/compare.html:238`: change
   `<td data-tone="cost">Browser refresh</td>` to
   `<td data-tone="win">HMR (@basenative/hmr)</td>`. Use `data-tone="win"`; the package's
   own README distinguishes state-preserving HMR from live reload, and the row's other three
   cells are scored `win` for the same capability.
2. **"Where others win"** — delete `examples/express/views/compare.html:293`. Do not soften
   it to "HMR is newer" — the list is specifically for capabilities BaseNative lacks, and it
   does not lack this one. The list keeps five honest entries without it.
3. **"Probably not"** — `examples/express/views/compare.html:324`: drop the HMR half and
   keep the devtools half, which is still true (`examples/express/views/compare.html:295`
   correctly notes there is no React DevTools equivalent). Rewrite as
   *"Apps where a mature devtools inspector is critical workflow."*
4. **Extend the guard** in `scripts/check-compare-page.js`. Add a
   `CAPABILITY_CLAIMS` table — a list of `{ phrase, packageDir }` pairs — and push a problem
   when the rendered page contains a negative phrase for a capability whose package exists
   in the workspace. Seed it with `{ phrase: /\bNo HMR\b/i, packageDir: 'hmr' }`.
   `scripts/compare-stats.js:119-128` already has `workspacePackages()`, which reads every
   `packages/*/package.json`, so the existence check is a filter over an existing helper —
   do not add a second directory walk.
5. Prefer extending `checkComparePage()` over adding a separate script: it is already called
   from both the build (`scripts/build-pages.js:67`) and the PR test suite
   (`tests/integration/integration.test.js:335`), so one edit gets both enforcement points.

## How we will know it worked

`checkComparePage()` returns a list of problem strings, and
`tests/integration/integration.test.js:333-340` already asserts that list is empty. After
step 4 and *before* steps 1–3, that test fails with `/compare disagrees with the source:
compare.html says "No HMR" but packages/hmr ships`. After steps 1–3 it passes. That is the
before/after pair:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative/tests && node --test integration/integration.test.js
```

and the build gate:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative && pnpm build:pages
```

which exits 1 via `scripts/build-pages.js:68-73` in the same interim state.

The remaining wording — whether "HMR (@basenative/hmr)" is the right cell text, whether the
"Probably not" rewrite still reads honestly — is copy, and no test settles it. Read the
rendered `/compare` end to end once after the change and confirm the page still reads as a
fair account rather than a pitch; that tone is the page's entire value.

## Notes

- **Do not type a number into `examples/express/views/compare.html`.** CLAUDE.md § Precedence
  is explicit: *"update a number on /compare" → `scripts/compare-stats.js` (measures it from
  source at build time)*, and `checkComparePage()` fails the build on a literal. This ticket
  changes prose cells only, which is allowed — but if the fix tempts you to write "21 source
  modules" or a version number into the view, bind it instead.
- Root cause shared with BN-057, BN-065 and BN-066: page copy asserting facts about the repo
  with nothing checking it. `/compare` is the only page with any guard at all, and this
  ticket widens that guard from numbers to capabilities. BN-065 asks for the same idea on
  `/roadmap`. If both are worked together, put the shared helper in
  `scripts/compare-stats.js`, which both would import — but neither ticket blocks the other.
- The memory note "BaseNative real adoption numbers" records that the compare page has
  previously shipped four false numbers. The numeric guard was the response to that. This is
  the same failure recurring in the half of the page the guard does not read — worth saying
  in the PR description.
- `packages/hmr` being version `0.2.0` is not a reason to keep the disclaimer. Check
  `docs/package-inventory.md` (generated — do not hand-edit) for its published state before
  writing the cell text, so the table does not over-claim in the other direction.
