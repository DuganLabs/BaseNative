## What the user hits

On a phone or tablet, calendar events cannot be moved at all. Touching and dragging a job block does nothing — no lift, no drop target, no save, and no message explaining why — so a dispatcher on site cannot reschedule anything. Keyboard-only users are in the same position on desktop: the blocks are `draggable` but there is no key that picks one up, so the entire scheduling feature is mouse-only. In GreenPut this is the *only* way to reschedule a job, so the product's core action is unreachable for touch and keyboard users.

## Why it happens

`packages/components/src/internal/drag.js:9-17` is a thin passthrough — it binds whatever handler names it is handed:

```js
export function bindDrag(el, handlers) {
  const entries = Object.entries(handlers).filter(([, fn]) => typeof fn === 'function');
  for (const [type, fn] of entries) el.addEventListener(type, fn);
  …
}
```

and both callers hand it only HTML5 drag events: `initCalendarDragDrop` at `packages/components/src/calendar.js:450-494` passes `dragstart`, `dragover`, `dragleave`, `drop`, `dragend` (with a second `bindDrag` for an external `dragSource` at `calendar.js:496-507`), and `initPipelineDragDrop` at `packages/components/src/calendar.js:555-606` passes the same five. The JSDoc type on `drag.js:6` even enumerates those five as the only allowed keys.

`grep -rnE 'pointerdown|touchstart|touchmove|pointermove|setPointerCapture' packages/components/src/` returns nothing. There is no pointer path, no tap-to-move, and no keyboard alternative anywhere in the package. A touch drag fires no `dragstart` on any mobile browser, so nothing is picked up, `drop` never runs, `onDrop` is never called, and no POST is made.

`slotMinute` at `packages/components/src/calendar.js:400-406` derives the drop minute from `e.clientY` against the slot's bounding box, so any replacement path has to supply a vertical coordinate or a minute directly.

Consumer: `/home/dugan/Developer/github.com/DuganLabs/GreenPut/apps/platform/src/routes/jobs/jobs.ts:440` binds `initCalendarDragDrop` as the only reschedule path in the product; `jobs.ts:424-434` is the `jobs.update({ scheduledStart, scheduledEnd })` call it drives.

This is a WCAG 2.2 AA failure on two counts: **2.5.7 Dragging Movements** (no single-pointer alternative to the drag) and **2.1.1 Keyboard** (no keyboard operation of the control).

## The fix

Chosen approach: add a **select-then-place** path — one tap/click to pick up an event, one tap/click on a target slot to drop it — and wire the same state machine to the keyboard. Select-then-place is the right choice over emulating drag with `pointermove`/`setPointerCapture`, because 2.5.7 asks specifically for an alternative that is *not* a dragging movement, and the same two-step machine satisfies 2.1.1 with no extra code. It also reuses `onDrop` verbatim, so no consumer changes.

1. Widen `packages/components/src/internal/drag.js`. Either drop the handler-name union in the JSDoc at `drag.js:6` so `bindDrag` accepts any event name (it already does at runtime — `drag.js:11` is a generic `addEventListener` loop), or leave `bindDrag` alone and add the new listeners in a second `bindDrag` call. Prefer widening the JSDoc: one binding site is easier to tear down in `destroy()`.
2. In `initCalendarDragDrop` (`packages/components/src/calendar.js:427`), add a module-scoped-per-instance `picked` variable and these handlers to the existing `bindDrag` call at `calendar.js:450`:
   - `click` — if the target is inside `[data-event-id]` or `[data-block-id]` and nothing is picked, set `picked` to `{ type, id }`, mark the element `data-picked`, and stop. If something *is* picked and the target is inside `[data-bn="calendar-slot"]`, call the same `onDrop({ eventId, date, hour, minute, datetime, sourceType })` payload the `drop` handler builds at `calendar.js:480-487`, then clear `picked`. For `minute`, reuse `slotMinute(e, slot, snapMinutes)` — a click carries `clientY`, so it works unchanged.
   - `keydown` — `Enter`/`Space` on a focused event picks it up or drops it on the currently focused slot; `ArrowUp`/`ArrowDown` move the pending target by `snapMinutes`; `ArrowLeft`/`ArrowRight` move it by one day; `Escape` clears `picked` and its `data-picked` attribute. Drive it off the slot's own `data-date`/`data-hour` attributes (`calendar.js:284`) rather than recomputing dates.
3. Make the pieces reachable and announced in `renderCalendar`:
   - add `tabindex="0"` to the event block at `packages/components/src/calendar.js:273` (it is a `<div>` today and is not focusable);
   - give it an `aria-describedby` pointing at one shared instruction node rendered once per calendar, e.g. "Press Enter to pick up, arrow keys to move, Enter to drop, Escape to cancel";
   - announce pick-up and drop through a polite live region rendered inside the calendar wrapper (`calendar.js:294`), updated by the handlers in step 2. Without it a keyboard user gets no feedback that anything was picked up.
4. Add a `[data-picked]` style to `packages/components/src/components.css` beside the existing `[data-bn="calendar-event"][data-dragging]` rule at `components.css:1559`, so the lifted state is visible.
5. Apply the same `click`/`keydown` pair to `initPipelineDragDrop` (`calendar.js:552`), where the drop target is `[data-bn="pipeline-column-cards"]` (`calendar.js:569`) and the payload is `onCardMove({ cardId, targetColumnId, position })` (`calendar.js:595-599`). `dropPosition` at `calendar.js:523-536` also reads `e.clientY` and works from a click; for the keyboard path pass the index directly.
6. Update the `initCalendarDragDrop` JSDoc at `packages/components/src/calendar.js:408-426` and the client-side section of `docs/api/components.md` to document the tap and keyboard paths as first-class, not as fallbacks.

## How we will know it worked

Add to `packages/components/src/components.test.js`, in the block that already exercises `initCalendarDragDrop` (search the file for `initCalendarDragDrop` — it uses a hand-rolled element/event stub; extend that stub with `click` and `keydown` dispatch rather than introducing a DOM library, since CLAUDE.md pins the suite to `node:test` with no extra dependencies):

```js
it('reschedules by tap-to-pick then tap-to-place, with no drag events', () => {
  const drops = [];
  initCalendarDragDrop(container, { onDrop: d => drops.push(d) });
  fire(eventBlock, 'click');                 // pick up
  fire(slotFor('2025-06-03', 14), 'click');  // place
  assert.equal(drops.length, 1);
  assert.deepEqual(
    { eventId: drops[0].eventId, date: drops[0].date, hour: drops[0].hour },
    { eventId: 'ev', date: '2025-06-03', hour: 14 },
  );
});

it('reschedules from the keyboard', () => {
  // focus the event, Enter, ArrowRight, Enter → onDrop fires one day later
});
```

Both fail before the change (`onDrop` is never called — only `drop` can call it, at `calendar.js:477`) and pass after. Run `cd packages/components && node --test`.

Also verify by hand on a real touch device (or Chrome DevTools device emulation with touch input) against `/components/calendar`: tap a block, tap a slot, confirm the block moves. Touch-drag behaviour cannot be asserted in `node:test`.

## Notes

- Keep the existing HTML5 drag path. It is the fastest gesture with a mouse, GreenPut depends on it (`jobs.ts:440`), and removing it would be a regression; the new path is additive and shares `onDrop`.
- Independent of **BN-010** and **BN-063**, but they touch the same file. BN-063 fixes the fact that the top hour band currently has *no* slot element at all — until that lands, a tap-to-place on the first visible hour will fail for the same reason a drag there fails, so land BN-010/BN-063 first or the new test's slot lookup will look flaky for the wrong reason.
- The audit that produced this finding also claimed the calendar "opens on SUN and never scrolls to today". That is **not** this package's defect and does not belong in this ticket: `renderCalendar` emits `data-today` on both the header and the column (`packages/components/src/calendar.js:243-247`), and the week start comes from GreenPut's own `weekStart()` at `jobs.ts:516`. Any fix for that belongs in the GreenPut repo.
- `bindDrag`'s `destroy()` (`drag.js:12-16`) removes exactly the listeners it added, and `initCalendarDragDrop` returns a composed `destroy()` at `calendar.js:509-514` that GreenPut pushes onto its cleanup list (`jobs.ts:444`). Any listener added outside `bindDrag` — a `document`-level `keydown`, for instance — must be removed there too, or the GreenPut route leaks a handler on every week change.
