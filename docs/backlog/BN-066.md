## What the user hits

Two things, both invisible to a casual visitor and both costly.

`/test-signals` is published to basenative.com and reachable by anyone who guesses or finds
the URL, but no link on the site points at it — while the 404 page tells every visitor who
mistypes a URL that *"every page on the site is reachable from the navigation above."* It is
an internal verification harness presented as a public page.

Separately, the site publishes no `sitemap.xml`, no `robots.txt` and no `llms.txt`. Crawlers
have to discover the ~40 pages by following links, and an LLM agent asking for
`basenative.com/llms.txt` — the convention this project itself generates a file for — gets a
404. For a framework whose pitch is being AI-native, that last one is the expensive half.

## Why it happens

**`/test-signals` is in the route table, so the build publishes it.**
`examples/express/page.js:164-170`:

```js
  {
    path: '/test-signals',
    view: 'test-signals.html',
    title: 'Signal Verification',
    activePage: '',
    ctx: () => ({ items: TEST_SIGNAL_ITEMS, itemsJson: JSON.stringify(TEST_SIGNAL_ITEMS) }),
  },
```

`scripts/build-pages.js:78-80` walks that table and writes every entry:

```js
for (const route of siteRoutes) {
  writePage(route.path, renderRoute(route, { tasks: staticTasks, hasApi: false }));
}
```

`dist/test-signals/` is present in the current build output.

Nothing links to it. `grep -rn 'test-signals' examples/express/ scripts/` returns three lines
and no link: the two route-definition lines above, plus
`scripts/audit/axe.mjs:37` (`'/test-signals/'` in the audit's page list). The nav menu
(`examples/express/views/layout.html:246-256`) has nine items and does not include it;
`navPages` (`examples/express/site-data.js:6-16`) lists nine names and does not include it;
`activePage: ''` is the giveaway that it was never meant to appear in the nav. The footer
(`examples/express/views/layout.html:263-270`, links at `:266-268`) links GitHub, Docs and Components only.

Meanwhile `examples/express/views/not-found.html:5-6`:

```html
    There is nothing at this address. The link may be out of date, or the URL may have a typo —
    every page on the site is reachable from the navigation above.
```

**The build copies assets but writes no discovery files.** `scripts/build-pages.js` copies
roughly two dozen named files (`scripts/build-pages.js:97-102`, `:104-115`, `:116`, the
component CSS list at `:121-130`, builder CSS at `:138-141`) and recursively copies the fonts
and icons directories (`scripts/build-pages.js:144`, `:147`), then writes `_headers`
(`scripts/build-pages.js:150-159`) and stops —
`console.log('Done → dist/')` at `scripts/build-pages.js:162`. `ls dist | grep -iE
'robot|sitemap|llms'` returns nothing. `llms.txt` and `llms-full.txt` *are* generated and
committed at the repo root (`scripts/llms-txt.js` owns them), so the content exists; the build
simply never copies it into `dist/`.

## The fix

Both halves are additions to `scripts/build-pages.js`, driven by the route table that already
exists. One PR.

1. **Stop publishing `/test-signals`.** Add a `internal: true` flag to its route entry at
   `examples/express/page.js:164-170` and skip flagged routes in the loop at
   `scripts/build-pages.js:78-80`. Prefer a flag over deleting the route: the Express dev
   server serves the same table, and the harness is genuinely useful locally — deleting it
   removes a working verification page to fix a publishing bug.
2. **Update `scripts/audit/axe.mjs:37`** in the same change. It currently audits
   `'/test-signals/'` against the built `dist/`; once the page is not published, that entry
   404s and the audit breaks. Either drop the entry or point the audit at the dev server for
   internal routes. Dropping it is simpler and correct — an unpublished page has no public
   accessibility surface.
3. **Emit `sitemap.xml`** from `siteRoutes` plus `flatComponents`. The build already iterates
   both (`scripts/build-pages.js:78-80` for routes,
   `scripts/build-pages.js:84-85` for `components/${component.slug}`), so collect the paths it
   writes and serialise them. Derive the URL list from the same loop that writes the pages,
   not from a second hand-maintained list — that is the whole lesson of BN-065.
4. **Emit `robots.txt`** with a `Sitemap:` line pointing at it. Write it next to the `_headers`
   write at `scripts/build-pages.js:159`, following that pattern.
5. **Copy `llms.txt` and `llms-full.txt`** from the repo root into `dist/`, alongside the
   existing `cpSync` calls. Copy rather than regenerate at build time: `scripts/llms-txt.js`
   owns those files and CI already fails on drift (CLAUDE.md § Precedence: *"update llms.txt /
   API docs" → `scripts/llms-txt.js` (regenerate)*; hand-editing them is explicitly wrong), so
   the committed files are authoritative and a second generation path could disagree with the
   one CI checks.
6. **Fix the 404's claim, or make it true.** After step 1 the statement at
   `examples/express/views/not-found.html:6` becomes accurate for the published site, so
   nothing more is needed — verify that rather than rewording it. If step 1 is deferred for any
   reason, the copy must change instead; do not ship both the unlinked page and the promise.

## How we will know it worked

The publish-set is derivable, so assert on it. Add to `tests/integration/integration.test.js`
beside `§ 12. /compare: published claims match the source`
(`tests/integration/integration.test.js:331-340`):

```js
// every published route must be reachable from the nav or the footer
import { siteRoutes } from '../../examples/express/page.js';
const layout = readFileSync('examples/express/views/layout.html', 'utf8');
for (const route of siteRoutes) {
  if (route.internal) continue;
  assert.ok(
    layout.includes(`href="${route.path}"`),
    `${route.path} is published but nothing in layout.html links to it — either link it or mark it internal`,
  );
}
```

That fails today on `/test-signals` and passes after step 1. It is the guard that generalises:
it catches the next route added without a nav entry, which is how this one got here.

For the discovery files, assert on the build output rather than the source — run
`pnpm build:pages`, then:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative
test -f dist/sitemap.xml && test -f dist/robots.txt && test -f dist/llms.txt && echo ok
test ! -d dist/test-signals && echo "test-signals correctly absent"
```

Both lines fail today. Better still, fold those four checks into `scripts/build-pages.js`
itself as a post-write assertion, next to the existing `assertNoEscapedMarkup` /
`assertNoDevScripts` guards (`scripts/build-pages.js:42`, `:58`) — the build refusing to
finish is stronger than a test someone has to remember to run.

The one thing no test settles: whether the sitemap should include `/components/*` (≈30 URLs)
or only the top-level routes. Include them — they are real indexable content pages, and they
are the ones a search engine would otherwise never find, since the catalogue links to them
from a single page.

## Notes

- Root cause shared with BN-029: nothing in the build checks the site's internal link graph is
  connected. BN-029 is the other end of the same problem — `/docs` contains zero `<a>` tags
  (`grep -c '<a ' examples/express/views/docs.html` = 0) and is a dead end. The reachability
  test in the section above is the shared guard; if both tickets are worked together, write it
  once. Neither blocks the other.
- **`scripts/audit/axe.mjs:37` is the reference the original audit missed.** Removing the route
  without touching the audit breaks `pnpm audit:axe`, which is part of `pnpm audit`
  (`package.json:13`). Step 2 is not optional.
- Do not add `/test-signals` to the nav as the fix. It is an internal signal-verification
  harness; a public nav entry to a test page is worse than an unlinked page.
- `_headers` (`scripts/build-pages.js:150-159`) sets a strict CSP. A `sitemap.xml` and
  `robots.txt` are static text and unaffected, but per the Cloudflare edge-injection memory
  note, confirm the final headers in a browser rather than with curl if anything about CSP
  changes — Cloudflare injects scripts after the origin responds.
- `activePage: ''` on the `/test-signals` route (`examples/express/page.js:168`) is a
  deliberate marker that the page has no nav
  item. Worth preserving as the signal for step 1's `internal` flag, or — better — deriving
  `internal` from `activePage === ''` so there is one source of truth rather than two flags
  that can disagree. Verified: `grep -n "activePage: ''" examples/express/page.js` returns only
  line 168, so `/test-signals` is the sole route with an empty `activePage` and the derivation
  is safe today.
