## What the user hits

On `/components/pagination` the first example shows a correct horizontal pager. The second
example, "Reactive page", shows a browser-default vertical numbered list — 1., 2., 3. down
the page with bullets' worth of indent — sitting directly beneath the correctly styled
"Page 3 of 10" label. The pager still works: clicking a number changes the page. It just
looks like the stylesheet failed to load for that one block, on the page whose whole job is
to show what the component looks like.

## Why it happens

Every layout declaration for pagination is scoped to `ul`, and the demo's client script
writes an `ol`.

`packages/components/src/components.css:539`:

```css
[data-bn="pagination"] ul {
  display: flex;
  list-style: none;
  padding: 0;
  margin: 0;
  gap: var(--bn-space-1);
}
```

The component emits `<ul>` — `packages/components/src/pagination.js:24`:

```js
let html = `<nav data-bn="pagination" aria-label="Pagination"><ul>`;
```

but the script that takes over the "Reactive page" example hand-writes an `<ol>` —
`examples/express/component-demo-scripts.js:208-210`:

```js
return '<nav data-bn="pagination" aria-label="Pagination"><ol>' +
  '<li>' + prev + '</li>' + arr.join('') + '<li>' + next + '</li>' +
  '</ol></nav>';
```

The effect runs on load (`examples/express/component-demo-scripts.js:212-215`), so the
server-rendered `<ul>` is replaced before the visitor ever sees it.

The item rules still apply, because they are descendant selectors that do not name the list
element: `packages/components/src/components.css:44-45` (`[data-bn="pagination"] a`,
`[data-bn="pagination"] span` in the shared control-height family) and
`packages/components/src/components.css:546`
(`[data-bn="pagination"] a, [data-bn="pagination"] span { display: inline-flex; … }`). That
is why the links themselves look right while the list around them is broken — which makes
the defect read as a rendering bug rather than a missing rule.

The site stylesheet adds no pagination rule of its own:
`grep -c pagination examples/express/public/styles.css` = `0`.

## The fix

Fix the CSS in the package, not the script in the demo. Pagination *is* semantically an
ordered list, so any consumer who reaches for `<ol>` deserves working styles — and the site
demo then stops being a special case.

1. In `packages/components/src/components.css`, change the selector at line 539 from
   `[data-bn="pagination"] ul` to `[data-bn="pagination"] :is(ul, ol)`. One character class,
   no specificity surprise: `:is()` takes the highest specificity of its arguments, and `ul`
   and `ol` are both type selectors, so the rule's weight is unchanged.
2. Leave `examples/express/component-demo-scripts.js:208-210` as it is. Changing the script
   to `<ul>` would hide the bug from this one page while leaving every consumer's `<ol>`
   broken — the "BaseNative is the library" rule: fix it upstream, not in the consumer.
3. Grep for the same pattern before closing: `grep -n '"pagination"] ul' packages/components/src/components.css`
   should return nothing afterwards, and check whether any other component's layout rule
   names a single list element while its render function or a demo uses the other
   (`grep -n '\] ul\b\|\] ol\b' packages/components/src/components.css`).

## How we will know it worked

`node:test` has no layout engine, so assert on the stylesheet contract in
`packages/components/src/components.test.js`:

```js
// fails before, passes after
const css = readFileSync(new URL('./components.css', import.meta.url), 'utf8');
assert.match(css, /\[data-bn="pagination"\]\s*:is\(ul,\s*ol\)\s*\{/);
assert.doesNotMatch(css, /\[data-bn="pagination"\]\s+ul\s*\{/);
```

A stronger and more durable assertion, if you want one: parse every
`[data-bn="pagination"] …` selector out of the stylesheet and assert none of them names
`ul` or `ol` alone.

Then check by hand, because this is a visual defect: `pnpm start`, open
`http://localhost:3000/components/pagination`, and confirm the second example renders as a
single horizontal row of controls identical in shape to the first. Before the change the two
examples look nothing alike.

## Notes

- BN-060 is the other pagination defect on the site (`/showcase`'s pager links to
  `?page=N` on a static host). Different mechanism, different file, but if both are being
  worked, note that `renderPagination` is the shared component — read
  `packages/components/src/pagination.js` once and address both.
- BN-057 records a third pagination issue: `examples/express/component-catalog.js:396`
  claims "first, prev, next, last" support that `pagination.js` does not implement. That is
  a copy/API claim, tracked there.
- Do not "simplify" by deleting `list-style: none` and relying on `display: flex` — flex
  items do not show markers in most engines, but `list-style` is not guaranteed off, and
  the declaration is also what keeps the `<ol>` numbers from appearing.
- Both example panes on this page are server-rendered first and then, for the scripted one,
  replaced on load. That pattern is why an escaped-markup or wrong-element bug in a
  `component-demo-scripts.js` block is invisible to `assertNoEscapedMarkup()` in
  `scripts/build-pages.js:42` — the guard only sees the server output.
