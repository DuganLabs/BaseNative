## What the user hits

On basenative.com's `/tasks`, a visitor types a task, presses add, and watches it appear in
the list, in the filtered view, and in the "N tasks total" counter. Everything behaves like a
working app that saved their work. Then they reload, and their tasks are gone — replaced by
the same three seed rows. Deleting behaves identically: the row disappears and comes back on
reload. Nothing on the page ever says the data is not persisted.

## Why it happens

The static build renders the page with the API flag off, and the client's fallback path is a
silent local-only write.

`scripts/build-pages.js:79`:

```js
writePage(route.path, renderRoute(route, { tasks: staticTasks, hasApi: false }));
```

`requestJson` short-circuits on that flag — `examples/express/views/tasks.html:57-58`:

```js
async function requestJson(url, options) {
  if (!hasApi) return null;
```

so every call returns `null`, and `addTask` falls through to its local branch —
`examples/express/views/tasks.html:79-81`:

```js
  } else {
    const task = { id: nextLocalId++, title, status: 'active' };
    taskSignal.set(prev => [...prev, task]);
  }
```

`deleteTask` does the same unconditionally at
`examples/express/views/tasks.html:87-89` — it awaits the (null) response and then mutates the
signal regardless.

Because `taskSignal` drives the list, the filtered `computed`, and the counters
(`examples/express/views/tasks.html:49-55`), the UI is fully consistent with a successful save.
There is no state anywhere that says otherwise.

The page's only copy about how it works is `examples/express/views/tasks.html:3`:

```html
  <p>Server-rendered initial state with client-side hydration for interactivity.</p>
```

which says nothing about persistence. On the Express dev server `hasApi` is true and the tasks
really do save, so the defect only exists on the published static site — which is where every
visitor meets it.

## The fix

Do both halves. The copy is what stops the page being dishonest; `localStorage` is what makes
it actually good, and it is a handful of lines.

1. **Say it on the page.** Add a line that renders only when `hasApi` is false — the view is
   already a BaseNative template with `hasApi` in context
   (`examples/express/views/tasks.html:6` binds it as `data-has-api="{{ hasApi }}"`), so use
   an `@if` block rather than client-side DOM insertion. Wording: *"This is the static demo —
   tasks you add are kept in your browser and are not saved to a server."*
2. **Persist to `localStorage`.** In `examples/express/views/tasks.html`, when `hasApi` is
   false, seed `taskSignal` from `localStorage` (falling back to the server-rendered seed rows)
   and write back inside an `effect()` on `taskSignal`. Wrap every read and write in
   `try/catch` — a private window or blocked site data makes the accessor itself throw — and
   render correctly with no stored value.
3. **Keep the fallback branch silent-but-honest, not removed.** Do not make `addTask` refuse
   to add when `hasApi` is false; an inert form on the flagship interactive demo is worse than
   a browser-local one. The defect is the missing disclosure and the missing durability, not
   the local write.
4. **Do not give the static build a real API.** That would mean a Worker or Pages Function for
   a demo page, and CLAUDE.md's deploy story is `wrangler pages deploy dist` of a static
   build. `localStorage` plus one line of copy is the proportionate fix.
5. Use the `hasApi === false` branch only. Leave the `res` path untouched so the Express dev
   server and `examples/enterprise*` behaviour are unchanged.

## How we will know it worked

The disclosure is server-rendered, so it is testable. Add to
`tests/integration/integration.test.js` next to
`§ 12. /compare: published claims match the source`
(`tests/integration/integration.test.js:331`) — this fails today:

```js
import { renderRoute, siteRoutes } from '../../examples/express/page.js';
const tasksRoute = siteRoutes.find((r) => r.path === '/tasks');
const staticHtml = renderRoute(tasksRoute, { tasks: [], hasApi: false });
assert.match(staticHtml, /not saved to a server/i,
  '/tasks must disclose that the static build does not persist');
const apiHtml = renderRoute(tasksRoute, { tasks: [], hasApi: true });
assert.doesNotMatch(apiHtml, /not saved to a server/i,
  'the disclosure must not appear when the API is live');
```

The two-sided assertion matters: it proves the `@if` actually keys on `hasApi` rather than
being unconditional copy.

The `localStorage` round-trip needs a browser. `tests/e2e/smoke.spec.js` exists and
`@playwright/test` is a devDependency — add a case against the built `dist/` (not the dev
server, which has the API): add a task, reload, assert it is still listed. That fails today.

## Notes

- The equivalent of this bug for a real product would be a data-loss incident; here it is a
  demo, which is why it is `annoying`. It is still the single most misleading interaction on
  the site, because the page succeeds visibly.
- `nextLocalId` (`examples/express/views/tasks.html:47`) is seeded from the maximum id in
  `initialData` — the three *server-rendered seed rows*. If you restore from `localStorage`,
  reseed it from the restored list instead, or a reload will mint ids 4, 5, 6 again and collide
  with the stored tasks that already hold them.
- Per the CLAUDE.md Constitution, Axiom 4 (Trinity Standard — state, logic and template fuse
  in one file), the `localStorage` code belongs in `tasks.html` alongside the signals, not in
  a new `public/tasks.js`. Do not split it out.
- The root cause family is shared with BN-057, BN-058 and BN-065: page copy that describes a
  capability without anything checking the claim. Here the copy's sin is omission rather than
  over-claim. The test above is the guard.
- Note the pattern for future demos: `renderRoute(route, { …, hasApi: false })` at
  `scripts/build-pages.js:79` silently degrades *every* route's API-dependent behaviour in the
  static build. `/tasks` is the only route that currently takes writes, but check this line
  before adding another interactive page.
