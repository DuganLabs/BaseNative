## What the user hits

A reader clicks **Docs** in the footer, or follows *"Read the API docs"* from the 404 page,
expecting the API reference the page's own search-result description promises for five
packages. They get five entries: `signal`, `computed`, `effect`, `hydrate` and `render`.
Nothing about the router, forms, or the 30 components they just browsed. Then they copy the
first code sample — `import { signal } from 'basenative'` — and it does not resolve, because
no package by that name exists. Four lines higher the same page has just told them the real
names are `@basenative/*` on GitHub Packages. There is also no way to navigate onward: the
page contains zero links.

## Why it happens

Three independent gaps, all in one view and its route metadata.

**1. The promise is in the route, the content is not in the view.**
`examples/express/page.js:128-129`:

```js
description:
  'API reference for @basenative/runtime, @basenative/server, @basenative/router, @basenative/forms, and @basenative/components.',
```

That string is the page's `<meta name="description">` and its search-result copy.
`grep -n 'router\|forms\|components' examples/express/views/docs.html` exits 1 — the view
mentions none of the three.

**2. Every import sample names a package that does not exist.** Five samples, all wrong:

- `examples/express/views/docs.html:14` — `import { signal } from 'basenative';`
- `examples/express/views/docs.html:35` — `import { signal, computed } from 'basenative';`
- `examples/express/views/docs.html:52` — `import { signal, effect } from 'basenative';`
- `examples/express/views/docs.html:70` — `import { signal, hydrate } from 'basenative';`
- `examples/express/views/docs.html:159` — `import { render } from 'basenative/server';`

`grep -l '"name": "basenative"' packages/*/package.json` returns nothing; the real names are
`@basenative/runtime` and `@basenative/server`. The page contradicts itself at
`examples/express/views/docs.html:4`, which explains how to point `.npmrc` at
`https://npm.pkg.github.com/` and authenticate for `@basenative/*` — and even warns that a
plain `npm install @basenative/runtime` resolves to stale builds. So the one paragraph that
gets the naming right sits directly above four samples that get it wrong.

**3. No navigation.** `grep -c '<a ' examples/express/views/docs.html` = `0`.

This is a high-traffic dead end: it is the target of the 404's secondary CTA
(`examples/express/views/not-found.html:11`) and the footer's Docs link
(`examples/express/views/layout.html:266`).

## The fix

Do the cheap correctness work first — it is the part that actively misleads — then close the
promise gap by narrowing the promise, not by writing three new API references inline.

1. **Fix the five import statements** in `examples/express/views/docs.html`. Lines 14, 35,
   52 and 70 become `from '@basenative/runtime'`; line 159 becomes
   `from '@basenative/server'`. Each is inside a `<span class="str">'…'</span>` in a
   syntax-highlighted `<pre><code>` block, so edit the string contents only and leave the
   markup alone.
2. **Add links.** At minimum: from each documented primitive to the generated reference for
   its package under `docs/api/`, and a "Full API reference" list linking the packages the
   description names. `docs/api/*.md` exists for every package (see CLAUDE.md § Shipped —
   *Documentation gaps (llms-full Gaps 77 → 0)*), so these are links to existing content,
   not new prose.
3. **Reconcile the description with the page.** Narrow `examples/express/page.js:128-129` to
   what the view actually documents — the runtime and server surface — and add a sentence
   pointing at `docs/api/` for the rest. Prefer narrowing the description over expanding the
   view: hand-writing router/forms/components references into `docs.html` duplicates
   `docs/api/*.md`, which is generated (CLAUDE.md § Precedence: *"update llms.txt / API
   docs" → `scripts/llms-txt.js` (regenerate)* — hand-editing is explicitly wrong), and a
   second hand-maintained copy is guaranteed to drift.
4. **Add the import-name guard** so this cannot recur. In
   `tests/integration/integration.test.js`, next to
   `§ 12. /compare: published claims match the source`
   (`tests/integration/integration.test.js:331-340`), assert that no view under
   `examples/express/views/` contains a `from 'basenative` string that is not
   `@basenative/…`. One regex over the view files; it fails today on five lines.

## How we will know it worked

The import half is testable and should fail before the fix:

```js
// tests/integration/integration.test.js — new section
const views = readdirSync(viewsDir).filter((f) => f.endsWith('.html'));
for (const f of views) {
  const src = readFileSync(join(viewsDir, f), 'utf8');
  assert.ok(
    !/from&nbsp;|from<\/span>\s*<span class="str">'basenative/.test(src) &&
      !/'basenative(?:\/|')/.test(src),
    `${f} imports from 'basenative' — the published names are @basenative/runtime and @basenative/server`,
  );
}
```

Note the samples are HTML-escaped and span-wrapped, so match on the quoted specifier
`'basenative'` / `'basenative/server'` rather than on a literal `import … from` sequence.

The link count is equally mechanical: assert `grep -c '<a '` on `docs.html` is greater than
zero, or in the test, `assert.ok(src.includes('<a '))`.

The description/content agreement is copy, and a test would only re-encode the same
judgement. Check by hand after the change: view source on `/docs`, read the
`<meta name="description">`, and confirm every package it names is either documented on the
page or linked from it.

  build and the unlinked `/test-signals` route. Both tickets are symptoms of the same thing

  could serve both, but neither ticket depends on the other.

  contradiction. That paragraph is correct and load-bearing — per the memory note on the
  BaseNative GitHub Packages org, packages live under the `basenative` org on GitHub

  to stale `0.2.x`/`0.3.x` builds.

  drift (CLAUDE.md § Precedence). Do not hand-edit `llms.txt`, `llms-full.txt` or
  `docs/package-inventory.md` while doing this work.
