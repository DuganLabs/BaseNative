## What the user hits

Someone drags a Button onto the Builder canvas, sets its variant to Primary, exports the
code, and pastes it into their app. They get a grey system button with a 3D bevel — the
browser's default — not the primary button they configured. Every component the Builder
exports is unstyled the same way. Worse, the Builder's own canvas shows the same unstyled
button, so the WYSIWYG preview is faithful to the broken export rather than to the library,
and nothing in the tool signals that anything is wrong.

## Why it happens

The Builder has no concept of the `data-bn` attribute contract that every rule in
`packages/components/src/components.css` is keyed on.
`grep -n 'data-bn\|dataBn' packages/builder/src/palette.js packages/builder/src/codegen.js`
exits 1 — the string does not appear in either file.

The palette registers a button as a plain `<button>` with `variant` as an ordinary prop —
`packages/builder/src/palette.js:128-141`, defaults at
`packages/builder/src/palette.js:140`:

```js
defaults: { text: 'Click me', variant: 'primary', type: 'button' },
```

Codegen then sends every unrecognised prop through its catch-all at
`packages/builder/src/codegen.js:72-74`:

```js
} else if (typeof value === 'string' || typeof value === 'number' || typeof value === 'boolean') {
  attrs += renderAttr(key, value);
}
```

so the export is:

```html
<button variant="primary" type="button">Click me</button>
```

The real component emits a different shape —
`packages/components/src/button.js:49`:

```js
return `<button data-bn="button" data-variant="${escapeAttr(variant)}" data-size="${escapeAttr(size)}" type="${escapeAttr(type)}"…>${slot}</button>`;
```

and every button rule in the shipped CSS selects on that, not on a bare `variant`:
`packages/components/src/components.css:139` `[data-bn="button"] { … }` and
`packages/components/src/components.css:162`
`[data-bn="button"][data-variant="primary"] { background: var(--bn-color-primary-600); … }`.
The button is also in the shared control-height family at
`packages/components/src/components.css:39-49`, again keyed on `[data-bn="button"]`. A bare
`variant` attribute is matched by no selector anywhere in the project, so the exported
button is not merely the wrong variant — it receives no BaseNative styling whatsoever.

The canvas has the identical bug at `packages/builder/src/dom-render.js:30-31`:

```js
if (value === true) el.setAttribute(key, '');
else el.setAttribute(key, String(value));
```

(`el.dataset.bnType = node.type` at `packages/builder/src/dom-render.js:20` sets
`data-bn-type`, which is the Builder's own selection bookkeeping — not `data-bn`, and not
matched by any component rule.)

## The fix

Teach the palette the attribute contract and have both emitters read it, rather than
special-casing per component in two places.

1. **Add two optional fields to each `palette.register()` entry** in
   `packages/builder/src/palette.js`: `bn` — the `data-bn` token the component emits
   (`'button'`, `'input'`, `'select'`, …) — and `dataProps` — the set of prop names that
   serialise as `data-*` rather than as bare attributes (for button: `['variant', 'size']`).
   Read the correct token and prop set for each entry straight out of the corresponding
   `packages/components/src/*.js` render function; do not infer them from the palette type
   name, which does not always match (`virtual-list` vs `data-bn="virtualizer"`).
2. **In `packages/builder/src/codegen.js`**, before the prop loop at
   `packages/builder/src/codegen.js:64`, emit `data-bn="<def.bn>"` when `def.bn` is set and
   `node.props['data-bn']` is absent — mirroring the existing `def.role` handling at
   `packages/builder/src/codegen.js:60-62`. Then inside the loop, when
   `def.dataProps?.includes(key)`, emit `renderAttr('data-' + attrName(key), value)` instead
   of falling through to the catch-all at
   `packages/builder/src/codegen.js:72-74`.
3. **Apply the same two rules in `packages/builder/src/dom-render.js`** at the matching
   points (`packages/builder/src/dom-render.js:22-24` for the `data-bn` emit,
   `packages/builder/src/dom-render.js:26-32` for the loop), so the canvas and the export
   produce byte-comparable attribute sets.
4. **Do not fix this by having the Builder call the `render*` functions.** It is the obvious
   move and it is wrong here: `packages/builder/src/dom-render.js` builds live DOM nodes that
   the inspector selects, drags and mutates, and `codegen.js` emits a BaseNative *template*
   with `@bind`/`{{ }}` bindings (`packages/builder/src/codegen.js:84-88`) that the render
   functions know nothing about. Swapping in HTML strings would break selection and drop
   every binding. Declaring the contract in the palette keeps one source of truth without
   changing either emitter's shape.
5. **Add a defaults audit while in `palette.js`:** any entry whose `defaults` contain a prop
   the component serialises as `data-*` but whose entry has no `dataProps` is a bug of this
   class. Fix all of them in one pass, not just the button.

## How we will know it worked

`packages/builder/src/codegen.test.js` and `packages/builder/src/palette.test.js` already
exist, so this is an addition to a live suite:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative/packages/builder && node --test
```

Add to `packages/builder/src/codegen.test.js` a case that fails today:

```js
// a button node exported from the palette defaults must carry the library contract
const html = generateCode(/* single button node with palette defaults */);
assert.match(html, /data-bn="button"/);
assert.match(html, /data-variant="primary"/);
assert.doesNotMatch(html, /<button[^>]*\svariant=/);
```

The strongest available assertion — and the one that would have caught this — is a
cross-check against the real component, since both are in this workspace. Add it to
`packages/builder/src/codegen.test.js`: for the button node, assert the exported tag's
attribute set is a superset of the `data-*` attributes in
`renderButton('Click me', { variant: 'primary' })`. Note `renderButton` also emits
`data-size="default"`, which the Builder has no prop for — decide in step 1 whether the
palette gains a `size` prop (preferred) or the assertion allows the component to have extras.

Add the canvas half to `packages/builder/src/builder-element.test.js`, which already runs
under `happy-dom`: render a button node and assert
`el.getAttribute('data-bn') === 'button'` and `el.dataset.variant === 'primary'`.

## Notes

- This is the *only* one of the journey findings where the defect ships to end users' own
  output rather than to a page on basenative.com — the exported code goes into their repo.
  That is why it stays `serious` despite a small diff.
- Keep `el.dataset.bnType` at `packages/builder/src/dom-render.js:20`. It is the Builder's
  selection key (used by the inspector and tree view), unrelated to `data-bn`, and removing
  it breaks selection.
- The Constitution's Axiom 1 (CLAUDE.md: *No namespace theater — semantic HTML only, W3C
  primitives are the component model*) is why the contract is an attribute on a real
  `<button>` rather than a custom element. The fix must not introduce a `<bn-button>`.
- Do not add a stylesheet to the Builder that matches bare `variant=` attributes to make the
  canvas look right. That would make the preview lie in the opposite direction and would
  leave the export — the artefact the user keeps — still broken.
- `packages/builder/src/escape.test.js` exists; `renderAttr` already escapes, so no new
  escaping work is needed for `data-*` names, but keep `attrName()` in the path so prop
  names are normalised the same way as today.
