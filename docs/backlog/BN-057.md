## What the user hits

Four component pages promise behaviour the component does not have. The worst is the
textarea: `/components/textarea` puts the words *"Type a longer message and watch this
textarea grow with the content…"* inside the box as placeholder text, and the box does not
grow. The reader types, watches nothing happen, and reasonably concludes the library is
broken rather than the copy. The other three are quieter: the pagination summary advertises
first/last buttons that are not rendered, the drawer summary says it slides in from any edge
when only left and right differ, and the select summary claims `appearance: base-select`
progressive enhancement that never reaches a BaseNative select.

## Why it happens

All four are copy in `examples/express/component-catalog.js` that outran the CSS.

**1. Textarea auto-sizing — the only `field-sizing` in the estate cannot match a BaseNative
textarea.** `grep -rn 'field-sizing' examples/express/public/styles.css packages/components/src/components.css`
returns exactly one hit: `examples/express/public/styles.css:696`, inside a block opened at
`examples/express/public/styles.css:684`:

```css
  textarea:not([data-bn]) {
    …
    field-sizing: content;
```

`packages/components/src/components.css` has no `field-sizing` declaration at all. And
`renderTextarea` emits `<textarea data-bn="textarea" …>` —
`packages/components/src/textarea.js:48` — which that `:not([data-bn])` selector explicitly
excludes. The claim appears in four places:

- `examples/express/component-catalog.js:83` — summary: *"Auto-sizing textarea with
  field-sizing: content and a vertical resize handle."*
- `examples/express/component-demos.js:177` — example title *"Auto-sizing"*
- `examples/express/component-demos.js:178` — description *"field-sizing: content lets the
  textarea grow with its value."*
- `examples/express/component-demos.js:182` — the placeholder quoted above

**2. Pagination first/last.** `examples/express/component-catalog.js:396`:

```js
summary: 'Page navigation with first, prev, next, last, and ellipsis handling.',
```

`packages/components/src/pagination.js` emits only `&laquo;` (prev,
`packages/components/src/pagination.js:28`) and `&raquo;` (next,
`packages/components/src/pagination.js:45`). Rendering the showcase's own call —
`renderPagination({ currentPage: 3, totalPages: 10, baseUrl: '/showcase' })` — produces 8
anchors: prev, 1, 2, 3, 4, 5, ellipsis, 10, next, with no first or last control. The first
and last page *numbers* do appear, via `computePages`, so this is an over-claim rather than a
fabrication.

**3. Drawer "any edge".** `examples/express/component-catalog.js:561`:

```js
summary: 'Side sheet for settings and secondary tasks. Slides in from any edge.',
```

`renderDrawer` writes whatever `position` it is given —
`packages/components/src/drawer.js:46` — but the stylesheet overrides only one value:
`grep -n '\[data-bn="drawer"\]' packages/components/src/components.css` gives the base rule
at `packages/components/src/components.css:1008` (`transform: translateX(100%)` at
`:1019`) and exactly one positional override at
`packages/components/src/components.css:1022` (`[data-bn="drawer"][data-position="left"]`).
`position="top"` and `position="bottom"` therefore render byte-identically to `right`. The
API table on the same page already tells the truth — `examples/express/component-catalog.js:567`
gives the type as `"'left' | 'right'"` — so the page contradicts itself.

**4. Select `base-select`.** `examples/express/component-catalog.js:102`:

```js
summary: 'Native select with appearance: base-select progressive enhancement.',
```

Correcting the original audit: `base-select` *is* in a stylesheet, but scoped away from the
component. `examples/express/public/styles.css:871-874`:

```css
  @supports (appearance: base-select) {
    select:not([data-bn]),
    select:not([data-bn])::picker(select) {
      appearance: base-select;
```

`packages/components/src/components.css` has no `base-select` rule, so a
`<select data-bn="select">` never gets it.

The common shape: `examples/express/public/styles.css` styles the *site's own* bare
elements and deliberately excludes `[data-bn]` so the component package wins — and the
catalogue copy was written against the site's capabilities rather than the package's.

## The fix

Two of these are best fixed by shipping the capability (it is a one-line declaration and the
copy is already written); two by correcting the copy. Take each on its merits rather than
uniformly.

1. **Textarea — ship it.** Add `field-sizing: content;` to the `[data-bn="textarea"]` rule in
   `packages/components/src/components.css`. The component already has a
   `min-block-size: var(--bn-control-height)` floor in the growable-controls group at
   `packages/components/src/components.css:54-59`, and the comment there says *"same starting
   height as a floor, never a hard cap"* — which is exactly the contract `field-sizing:
   content` needs. Shipping beats deleting four pieces of copy that describe a genuinely
   desirable behaviour, and `field-sizing` degrades silently where unsupported.
2. **Select — ship it too.** Add the `@supports (appearance: base-select)` block to
   `packages/components/src/components.css` for `[data-bn="select"]` and
   `[data-bn="select"]::picker(select)`, mirroring
   `examples/express/public/styles.css:871-878`. Same reasoning: progressive enhancement
   inside `@supports`, no risk to non-supporting engines, and the claim becomes true for
   every consumer rather than only for the demo site's unstyled selects.
3. **Pagination — correct the copy.** Change
   `examples/express/component-catalog.js:396` to *"Page navigation with prev, next, and
   ellipsis handling."* Do **not** add first/last buttons here: that is an API change to a
   published component (new options, new markup, new a11y labels) and needs its own ticket
   and changeset, not a copy fix.
4. **Drawer — correct the copy.** Change
   `examples/express/component-catalog.js:561` to *"Side sheet for settings and secondary
   tasks. Slides in from the left or right."* to match the API table two lines below at
   `examples/express/component-catalog.js:567`. Do not implement top/bottom: the base rule's
   `width: 20rem` and `data-size` variants (`packages/components/src/components.css:1018`,
   `:1028-1029`) are all inline-axis, so a real top/bottom drawer needs a block-axis sizing
   story — again, its own ticket.
5. After (1), re-read the four textarea copy sites and confirm they are now accurate rather
   than deleting them. After (2), the select summary stands as written.

## How we will know it worked

For the two shipped capabilities, assert the stylesheet contract in
`packages/components/src/components.test.js` — these fail today:

```js
const css = readFileSync(new URL('./components.css', import.meta.url), 'utf8');
assert.match(css, /\[data-bn="textarea"\][^{]*\{[^}]*field-sizing:\s*content/s);
assert.match(css, /appearance:\s*base-select/);
```

For the two copy corrections, the durable test is a claim-vs-source check, not a string
match. Add a section to `tests/integration/integration.test.js` next to
`§ 12. /compare: published claims match the source`
(`tests/integration/integration.test.js:331-340`) asserting, for each catalogue entry whose
summary names a control (`first`, `last`) or a direction (`top`, `bottom`), that the string
appears in the component's rendered output or in a positional CSS selector. That is the guard
that would have caught all four.

The textarea behaviour itself needs a hand check, since `node:test` and `happy-dom` do no
layout: `pnpm start`, open `http://localhost:3000/components/textarea`, type several lines
into the Auto-sizing example and confirm the box grows. Do the same for `/components/select`
in a Chromium build that supports `appearance: base-select` — confirm the custom picker
appears, and confirm in Firefox/Safari that the select still renders normally.

## Notes

- Root cause shared with BN-058, BN-065 and BN-066: the site has exactly one guard against
  claim/source drift, `checkComparePage()` (`scripts/check-compare-page.js:37`, called from
  `scripts/build-pages.js:67`), and it covers only `/compare`. Every other page's claims are
  unchecked. The claim-vs-source test in the section above is the smallest extension of that
  idea to the catalogue; if BN-058 is worked at the same time, build one shared helper.
- Why `examples/express/public/styles.css` uses `:not([data-bn])` everywhere: the site's own
  chrome (forms on `/tasks`, `/playground`) uses bare HTML elements, and the exclusion keeps
  the site's house style from fighting the component package. Preserve that — the fix is to
  add rules to the package, never to loosen the site's `:not([data-bn])` guards.
- Items 3 and 4 look like under-delivery, and they are, but both components' API tables
  already document the real surface; only the one-line summaries over-promise. Keep the fix
  to the summaries.
- Changing `packages/components/src/components.css` requires a changeset. CLAUDE.md marks
  `.changeset/*` as orchestrator-only for subagents — report the needed changeset upward
  rather than writing one if you are not the orchestrator.
