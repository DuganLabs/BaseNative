## What the user hits

Two demos on the component pages do not do what their buttons say. On
`/components/accordion`, pressing **Expand all** opens the third section only — the first two
flash open and snap shut. On `/components/dialog`, the × in the dialog's corner does nothing:
clicking it leaves the dialog open, and the visitor has to find Cancel or press Escape. The
Source pane beside the dialog makes it worse by claiming a backdrop click closes it, which it
does not.

## Why it happens

Two unrelated mechanisms.

**Accordion: the demo fights the component's exclusivity.** `renderAccordion` gives every
`<details>` a shared `name` unless `multiple` is passed —
`packages/components/src/accordion.js:27`:

```js
const exclusiveName = multiple ? '' : ` name="${escapeAttr(id)}"`;
```

applied to each item at `packages/components/src/accordion.js:32`. A shared `name` on
`<details>` is the native exclusive-accordion feature: opening one closes its siblings.

The "Expand / collapse all" example (`examples/express/component-demos.js:657` onward) does
*not* pass `multiple` — its `renderAccordion({ items: [...] })` call at
`examples/express/component-demos.js:666-672` has three items and no `multiple: true`. The
script then loops over them setting `open` —
`examples/express/component-demo-scripts.js:165`:

```js
accSlot.querySelectorAll('details').forEach((d) => { d.open = open(); });
```

In an exclusive group each assignment closes the previous one, so after the loop only the
last `<details>` is open. The Source pane teaches the same loop verbatim at
`examples/express/component-demos.js:674-683`, so a reader copying it inherits the bug.

**Dialog: the close button has no listener on this page.** `renderDialog` emits the × by
default — `closable = true` at `packages/components/src/dialog.js:39`, the button at
`packages/components/src/dialog.js:53-55`:

```js
  const closeBtn = closable
    ? `<button data-bn="dialog-close" aria-label="Close" type="button">&times;</button>`
    : '';
```

but the component page's script wires only three selectors —
`examples/express/component-demo-scripts.js`, `dialog:` block:
`[data-bn-demo-dialog-open]` → `showModal()`, `[data-bn-demo-dialog-cancel]` → `close()`,
`[data-bn-demo-dialog-confirm]` → `close()`. There is no handler for
`[data-bn="dialog-close"]`. `/showcase` does wire it —
`examples/express/public/showcase.js:75-77`:

```js
  for (const closer of document.querySelectorAll('[data-bn="dialog-close"]')) {
    closer.addEventListener('click', () => closer.closest('[data-bn="dialog"]')?.close());
  }
```

so the same markup works on one page and not the other.

And the snippet's comment is wrong — `examples/express/component-demos.js:1081`:

```js
// Native: backdrop click + Escape close it.
```

A native `<dialog>` closes on Escape only. Backdrop dismissal requires
`closedby="any"` (or a light-dismiss handler), and `grep -n closedby
packages/components/src/dialog.js` returns nothing.

Escape and Cancel both still dismiss the dialog, so there is a workaround — annoying, not
serious.

## The fix

1. **Accordion — pass `multiple: true`** in the "Expand / collapse all" demo at
   `examples/express/component-demos.js:666`, and update the Source pane at
   `examples/express/component-demos.js:674-683` to show it:
   `renderAccordion({ multiple: true, items: [...] })` above the loop. Fix the demo rather
   than the component: exclusive-by-default is a deliberate, documented behaviour (the native
   `name` attribute is the whole point of the implementation), and a demo whose button says
   "Expand all" is the one place `multiple` obviously belongs. Do not remove
   `exclusiveName`.
2. **Dialog close button — wire it** in the `dialog:` block of
   `examples/express/component-demo-scripts.js`, copying the pattern from
   `examples/express/public/showcase.js:75-77`. Add
   `document.querySelector('[data-bn="dialog-close"]')?.addEventListener('click', () => dlg?.close());`
   next to the existing cancel/confirm lines.
3. **Snippet comment — make it true.** Replace
   `examples/express/component-demos.js:1081` with
   `// Native: Escape closes it. Wire [data-bn="dialog-close"] for the × button.` Correct the
   comment rather than adding `closedby="any"` to `renderDialog`: that is an API/behaviour
   change to a published component, it changes dismissal semantics for every existing
   consumer, and it needs its own ticket plus a changeset. The demo's job is to describe what
   the component does today.
4. Also check the drawer block directly below the dialog block in
   `examples/express/component-demo-scripts.js` — it *does* wire both
   `[data-bn="drawer-overlay"]` and `[data-bn="drawer-close"]`, which is the shape the dialog
   block should match. Use it as the local model.

## How we will know it worked

The accordion half has a real unit test, in the component package — this fails before,
passes after, because it asserts the demo's own call produces an independently-openable
group:

```js
// packages/components/src/components.test.js
import { demos, getDemo } from '../../../examples/express/component-demos.js';
const html = getDemo('accordion').examples.find((e) => e.title === 'Expand / collapse all').html;
const names = [...html.matchAll(/<details[^>]*\sname="/g)];
assert.equal(names.length, 0, 'the expand-all demo must render a non-exclusive accordion');
```

If importing the example app from the package test is unwanted (it crosses a package
boundary), put the same assertion in `tests/integration/integration.test.js` alongside
`§ 12` (`tests/integration/integration.test.js:331`), which already imports from
`examples/express/`. Prefer that location.

The dialog listener is DOM behaviour. `tests/e2e/smoke.spec.js` exists and Playwright is a
devDependency — add a case there: navigate to `/components/dialog`, click the open trigger,
click `[data-bn="dialog-close"]`, assert the dialog is closed. That fails today.

The snippet comment is copy: read `/components/dialog`'s Source pane by hand after the change
and confirm it no longer promises backdrop dismissal.

## Notes

- BN-027 covers the broader Source-pane problem in the same two files (15 unparseable
  snippets, six snippets naming a client API that does not exist). The wrong comment here is
  the same root cause — Source strings authored independently of the code that runs — but the
  three edits in this ticket are small and specific; do not wait on BN-027, and do not
  fold BN-027's guard work in here.
- `accordion ex0`'s snippet is one of BN-027's 15 unparseable ones
  (`examples/express/component-demos.js:654` — `items: [{ title, content }, ...]`). The
  example this ticket fixes is `ex1`, a different snippet on the same page. Don't be confused
  by both being "the accordion snippet".
- Why the accordion bug looks like a rendering glitch rather than a state bug: the loop is
  synchronous, so all three sections genuinely do open in turn within one frame; the browser
  only paints the final state.
- `signal(null)` as the initial value in the accordion script
  (`examples/express/component-demo-scripts.js:162`, with the `if (open() === null) return;`
  guard at `:164`) is deliberate — it stops the effect from clobbering the server-rendered
  open state on load. Keep it.
