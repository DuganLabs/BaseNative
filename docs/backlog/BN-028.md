## What the user hits

`/components/virtual-list` is the one blank pane in the whole catalogue. Where the other 29
component pages show a working render, this one shows a two-pixel vertical hairline on the
checkerboard background and nothing else — no rows, no scroll port, no hint that a
virtualizer exists. A reader evaluating BaseNative concludes the component is unfinished.

## Why it happens

The virtualizer's own markup gives it a height but never a width, and its only descendant
is absolutely positioned, so it has nothing to size against.

`packages/components/src/virtualizer.js:54-56` is the whole structure:

```js
return `<div data-bn="virtualizer" id="…" tabindex="0" role="region"… style="height:${Number(containerHeight)}px;overflow:auto"…>
  <div data-bn="virtual-spacer" style="height:${Number(totalHeight)}px;position:relative">
    <div data-bn="virtual-window" style="position:absolute;top:0;left:0;right:0" …>
```

`virtual-window` is `position:absolute`, so it is out of flow and contributes nothing to its
ancestors' intrinsic width. `virtual-spacer` therefore has a min-content width of 0, and so
does `virtualizer`.

Its parent on the component page is the preview pane's `<output>`, which is a flex
container — `examples/express/public/styles.css:2725-2732`:

```css
[data-bn-component-preview] {
  & > output {
    display: flex;
    flex-wrap: wrap;
    gap: var(--space-md);
    align-items: center;
```

so the virtualizer is a flex item whose `flex-basis: auto` resolves to a content width of 0.
It collapses to its two 1px borders.

Nothing supplies a width. The package rule
(`packages/components/src/components.css:1460-1464`) sets only `overflow`, `border` and
`border-radius`:

```css
[data-bn="virtualizer"] {
  overflow: auto;
  border: var(--bn-border-width) solid var(--bn-color-border);
  border-radius: var(--bn-radius-lg);
}
```

and the site's own rule (`examples/express/public/styles.css:2073-2075`) adds only
`background: var(--surface-1)`.

Separately confirmed and **out of scope here**: there is no windowing client at all.
`grep -rn 'export function init' packages/components/src/` returns only `initTabs`
(`packages/components/src/tabs.js:80`), `initCalendarDragDrop` and `initPipelineDragDrop`
(`packages/components/src/calendar.js:427`, `:552`). No `initVirtualList` exists, so
scrolling never re-windows the item set. That gap belongs to BN-018.

## The fix

Fix it in the package, not the site: the collapse happens to every consumer who puts a
virtualizer in a flex container, not only to this page.

1. In `packages/components/src/components.css`, extend the `[data-bn="virtualizer"]` rule
   (line 1460) with `inline-size: 100%;`. Prefer `inline-size: 100%` over `flex: 1`: the
   virtualizer is not necessarily a flex item, and `100%` gives it a definite width in
   block layout too, whereas `flex: 1` is inert outside a flex parent.
2. Leave `packages/components/src/virtualizer.js` alone. Adding a width to the inline
   `style=""` would violate Axiom 2 of the Constitution (CLAUDE.md: *Zero inline styles —
   all CSS lives in cascade layers*). The existing `height`/`position` inline styles are
   grandfathered because they are computed per call; a constant `100%` is not, and belongs
   in the stylesheet.
3. Do **not** add a site-level override in `examples/express/public/styles.css`. That would
   make the demo page look right while every downstream consumer stayed broken — the exact
   failure mode the "BaseNative is the library" memory note warns about.
4. While in the rule, confirm the pane has a visible scrollbar: `overflow: auto` plus the
   inline `height:400px` means `totalHeight > 400` produces one. The showcase call already
   passes enough items; verify rather than change.

## How we will know it worked

There is no existing test for this. Add one to `packages/components/src/components.test.js`
that renders the virtualizer and asserts the CSS contract, since a `node:test` run has no
layout engine:

```js
// fails before, passes after
const css = readFileSync(new URL('./components.css', import.meta.url), 'utf8');
const rule = css.match(/\[data-bn="virtualizer"\]\s*\{[^}]*\}/)[0];
assert.match(rule, /inline-size:\s*100%/);
```

That is a proxy, not a proof. The real check is by hand, and it is quick: run
`pnpm start`, open `http://localhost:3000/components/virtual-list`, and confirm the preview
pane shows a full-width bordered box ~400px tall containing visible rows. Compare against
`/components/table`, whose pane is correct, to confirm the width now matches. `happy-dom`
is already a devDependency but does not do layout, so it cannot substitute for this.

## Notes

- **The missing windowing client is BN-018, not this ticket.** BN-018 covers the same gap
  across eight components; adding an `initVirtualList` here would duplicate that work and
  land it in the wrong place. This ticket is one CSS declaration. The page will still not
  re-window on scroll after this fix — that is expected and correct for this ticket's scope;
  it will show the first window of items, which is enough to stop the pane being blank.
- The audit originally graded this medium because it conflated the two problems. It is
  small once the windowing client is separated out.
- Why the site stylesheet's `background: var(--surface-1)` did not reveal the bug earlier: a
  0-width element with a background paints nothing, so the page looked merely empty rather
  than broken.
- `[data-bn="virtual-window"] { position: relative; }` at
  `packages/components/src/components.css:1465` is dead as written — the inline
  `position:absolute` from `virtualizer.js:56` always wins. Not worth a separate ticket, but
  worth deleting in the same PR rather than leaving a rule that implies the window is in
  flow.
