## What the user hits

A visitor lands on `/components/combobox`, likes what they see, and presses Copy on the
code block. What they paste into their editor does not parse — it contains a literal
`[...]` where the data should be. The same is true on `/components/multiselect`,
`/components/tree` and `/components/dropdown-menu`, where *both* snippets on the page are
broken, so those four pages ship nothing a reader can run. On six other pages the snippet
teaches a `renderBadge(...)`/`renderCard(...)` call in the browser that the shipped client
bundle does not export, so following the example throws `renderBadge is not defined`. Four
more panes print one render call next to five rendered elements, so the reader cannot tell
which call produced what.

## Why it happens

Three separate defects, all in the demo data that feeds the Source pane.

**1. `[...]` is elision, not code.** The demo authors abbreviated array arguments with a
bare spread of nothing. `examples/express/component-demos.js:366`:

```js
code: code(`renderCombobox({ name: 'framework', label: 'Framework', items: [...] })`),
```

`[...]` is a syntax error (`Unexpected token ']'`). Enumerating every snippet through
`getDemo()` (`examples/express/component-demos.js:1184`) and running `node --check` on each
gives **78 snippets across 30 components, 15 of which fail, every one with
`Unexpected token ']'`**: `radio ex0`, `combobox quickstart`, `combobox ex0`,
`multiselect quickstart`, `multiselect ex0`, `accordion ex0`, `tabs ex0`,
`breadcrumb ex0`, `table quickstart`, `table ex0`, `datagrid quickstart`,
`tree quickstart`, `tree ex0`, `dropdown-menu quickstart`, `dropdown-menu ex0`.

`combobox`, `multiselect`, `tree` and `dropdown-menu` each have exactly one example
(`examples/express/component-demos.js`, `getDemo(slug).examples.length === 1`), so their
quickstart *and* their only example are both broken — those four pages contain no
parseable JavaScript at all.

**2. Six scripted examples document a client render API that is not exported.** The Source
panes at `examples/express/component-demos.js:572` (`effect(() => slot.innerHTML =
renderBadge(unread(), {`), `:613` (`renderCard`), `:760` (`renderAvatar`), `:525`
(`renderSkeleton`), `:430` (`renderAlert`) and `:817` (`renderPagination`) all call a
`render*` function from browser code. The client bundle's export list
(`examples/express/public/basenative.js:1832-1875`) contains no `render*` export except
`renderWithBoundary`. What actually runs on the page hand-writes HTML strings instead —
e.g. `examples/express/component-demo-scripts.js:135`:

```js
badgeSlot.innerHTML = '<span data-bn="badge" data-variant="' + variant + '">' + unread() + '</span>';
```

So the pane teaches an API the page itself could not use.

**3. Four panes miscount the render beside them.** Rendering each example's `html` and
counting `data-bn="<slug>"` against the `render*(` calls in its `code`: badge *Variants*
renders 5 for 1 call, spinner *Sizes* 3 for 1, alert *Variants* 4 for 3, button *Disabled*
2 for 1.

All of this sits under `examples/express/views/component.html:40`, which claims *"Each
block is a real server render — no mockups, no virtual DOM."* The Copy button
(`examples/express/views/component.html:148-149`) hands over `pre.textContent` verbatim, so
there is no sanitising step between the broken string and the user's clipboard.

## The fix

Fix the data, then add the guard that stops it recurring — the guard is the durable half,
and the build already has precedent for refusing to publish a bad page
(`scripts/build-pages.js:42` `assertNoEscapedMarkup()`, `scripts/build-pages.js:67`
`checkComparePage()`).

1. **Replace every `[...]` with real, short, runnable data** in
   `examples/express/component-demos.js`. Do not substitute a comment or `/* … */` — the
   guard in step 4 parses these strings, and the reader's clipboard needs working code.
   Reuse a trimmed version of the array already passed to the live render a few lines
   above; e.g. for combobox, `items: ['React', 'Vue', 'Svelte']`. The 15 sites are the ones
   enumerated above; find them with
   `grep -n '\[\.\.\.\]' examples/express/component-demos.js`.
2. **Rewrite the six client-side snippets to the API that actually exists.** Make each
   Source pane match the code in `examples/express/component-demo-scripts.js` for the same
   `scripted:` key, rather than inventing a client `render*`. Prefer this direction over
   exporting `render*` from the client bundle: `@basenative/components` is a server-render
   package, shipping its 30 render functions into the browser bundle would blow the
   `<10KB gzipped` budget invariant in CLAUDE.md, and the honest lesson of the page is that
   BaseNative updates the DOM from signals rather than re-rendering components.
3. **Make the four miscounting panes agree with what they render.** Either show all the
   calls (badge *Variants*: five `renderBadge` lines) or reduce the rendered `html` to one
   element. Showing all the calls is better — the pane's job is to name the variants.
4. **Add `assertDemoSnippetsParse()` to `scripts/build-pages.js`,** called next to
   `checkComparePage()` at `scripts/build-pages.js:67`, before the first page is written.
   It should import `demos`/`getDemo` from `examples/express/component-demos.js`, walk
   every `quickstart` and every `examples[].code`, and for each string call
   `new vm.SourceTextModule(code)` (or `node:module`'s syntax check via a
   `vm.Script('(async()=>{' + stripped + '})')` fallback) — and `process.exit(1)` with the
   `slug/label` of each failure. Snippets are ESM (`import … from '@basenative/components'`),
   so a plain `new vm.Script(code)` rejects every quickstart for the wrong reason; the
   simplest correct check is to write each snippet to a temp `.mjs` and shell `node --check`,
   but an in-process `vm.SourceTextModule` under `--experimental-vm-modules` avoids the temp
   files. Pick `vm.SourceTextModule`.
5. **Also assert every component page has at least one parseable snippet,** so the
   "four pages with zero runnable code" state can never come back even if the snippet count
   changes.

## How we will know it worked

Before the change, this fails with 15 names; after, it prints nothing:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative
node --experimental-vm-modules -e "
import('./examples/express/component-demos.js').then(async ({demos,getDemo})=>{
  const vm=await import('node:vm'); let bad=0,total=0;
  for(const k of Object.keys(demos)){const d=getDemo(k);
    const s=[['quickstart',d.quickstart],...(d.examples||[]).map((e,i)=>['ex'+i,e.code])];
    for(const [l,c] of s){ if(typeof c!=='string')continue; total++;
      try{new vm.SourceTextModule(c);}catch(e){bad++;console.log('BAD',k,l,e.message);}}}
  console.log(total+' snippets, '+bad+' bad');});
"
```

Land that as a test in `tests/integration/integration.test.js` — add a section alongside
`§ 12. /compare: published claims match the source`
(`tests/integration/integration.test.js:331-340`), which is the existing home for
"the published site tells the truth" assertions. `pnpm build:pages` must then also fail
before the data fix and pass after, proving the build guard is wired.

The client-API half (defect 2) and the miscount half (defect 3) are not caught by a parser.
Check those by hand: open `/components/badge`, `/components/card`, `/components/avatar`,
`/components/skeleton`, `/components/alert`, `/components/pagination` and confirm the
Source pane names only functions that exist in
`examples/express/public/basenative.js:1832-1875` plus DOM calls; and that the number of
`render*` calls shown matches the number of elements in the pane beside it.

## Notes

- The three defects share one root cause worth naming in the PR: the Source pane's string
  is authored independently of both the server render (`html:`) and the client script
  (`examples/express/component-demo-scripts.js`), with nothing tying the three together.
  Step 4's guard only closes the parse half. A follow-up worth considering — not in scope
  here — is deriving the scripted snippets *from* `component-demo-scripts.js` so they
  cannot drift again. This is the same family of failure the memory note
  "Tests stub their own contracts" describes.
- `scripts/build-pages.js:58` already runs `assertNoEscapedMarkup(assertNoDevScripts(...))`
  on every page; follow that pattern for naming and error-message style (CLAUDE.md: *error
  messages must be actionable — tell users WHAT to fix*). Both existing guards throw with
  the offending text and the route.
- Do not "fix" the `[...]` by deleting the `items` argument: several of these components
  render nothing without items, and the snippet would then be runnable but wrong.
- BN-036 and BN-059 also live in `component-demos.js` / `component-demo-scripts.js`. They
  are separate defects (a wrong element name, a missing listener) and should not be folded
  into this PR, but a single pass over those two files can carry all three cheaply.
- CLAUDE.md forbids subagents from editing `package.json`, `.github/workflows/*` and
  `nx.json`. Step 4 needs none of them — `scripts/build-pages.js` already runs under
  `pnpm build:pages`, and the test lands in the existing `tests/integration` suite.
