## What the user hits

On a phone, the × that dismisses an alert is about 11×18 CSS pixels — the size of the glyph
itself — so a thumb misses it as often as it lands, and the alert stays on screen. Breadcrumb
links are the height of their text line, roughly 23px, with no padding, so tapping a crumb to
go back up a level is fiddly and often lands on the separator instead. This ships in
`@basenative/components`, so every consumer inherits it, not just basenative.com.

## Why it happens

The stylesheet already has a deliberate WCAG 2.5.8 block and a token for exactly this — these
two controls were simply never added to it.

`packages/components/src/tokens.css:245-247` defines the floor:

```css
    /* Minimum interactive target size — WCAG 2.5.8 (24×24 CSS px). Applied as a hit-area
       floor via min-inline-size/min-block-size; never changes a control's visible glyph. */
    --bn-target-size-min: 1.5rem;
```

and `packages/components/src/components.css:101-134` applies it, by two different strategies
depending on whether the control's box can grow. `tree-toggle` grows directly
(`packages/components/src/components.css:109-112`); `tag-remove`, `checkbox`, `radio` and the
datagrid checkbox get an invisible centred `::before` hit region
(`packages/components/src/components.css:121-134`). `[data-bn="toggle-label"]` takes a third
route at `packages/components/src/components.css:257`.

**`alert-dismiss` is in neither.** Its only rules are the shared button reset at
`packages/components/src/components.css:84-99` (which sets appearance, border, background,
colour, text-align, cursor — no sizing) and its own block at
`packages/components/src/components.css:445-453`:

```css
[data-bn="alert-dismiss"] {
  margin-left: auto;
  background: none;
  border: none;
  cursor: pointer;
  font-size: var(--bn-font-size-lg);
  line-height: 1;
  opacity: 0.6;
}
```

No width, no height, no padding, and `line-height: 1` on a `&times;` glyph collapses the
button's box onto the glyph's box — the ~11×18 measured.
`grep -n 'alert-dismiss' packages/components/src/*.css` returns only lines 91, 445, 454 and
455; nothing else sizes it.

**`breadcrumb-item a` is in neither either.**
`packages/components/src/components.css:728-731`:

```css
[data-bn="breadcrumb-item"] a {
  color: var(--bn-color-text-link);
  text-decoration: none;
}
```

on an inline anchor inheriting `--bn-font-size-sm` from
`packages/components/src/components.css:717`, so the target is the text line box.
`grep -n 'breadcrumb' packages/components/src/*.css` shows rules at 717, 718, 727, 728, 732,
733, 734, 735 — none of them sizes the anchor.

Neither appears in `examples/express/public/styles.css` either
(`grep -n 'alert-dismiss\|breadcrumb\|tag-remove' examples/express/public/styles.css` → no
match), so nothing downstream compensates.

## The fix

Extend the block that already exists. Do not invent a new pattern or a new token.

1. **`alert-dismiss` — grow the box directly**, the `tree-toggle` treatment. Add it to the
   selector at `packages/components/src/components.css:109` so the rule becomes
   `[data-bn="tree-toggle"], [data-bn="alert-dismiss"] { min-inline-size: var(--bn-target-size-min); min-block-size: var(--bn-target-size-min); }`,
   and add `display: inline-flex; align-items: center; justify-content: center;` to
   `packages/components/src/components.css:445` so the × centres in the enlarged box instead of
   sitting top-left. Direct growth rather than the `::before` region: the dismiss button sits
   in an alert row with vertical space to spare and `margin-left: auto` pushing it to the edge,
   so a 24×24 box changes nothing visible — which is the condition the comment at
   `packages/components/src/components.css:103-105` gives for choosing this strategy.
2. **`breadcrumb-item a` — padding, not a fixed height.** At
   `packages/components/src/components.css:728` add
   `display: inline-flex; align-items: center; min-block-size: var(--bn-target-size-min); padding-inline: var(--bn-space-1);`.
   Padding rather than `block-size`: crumb text can wrap on narrow viewports and a fixed height
   would clip it. Keep the anchor inline-level so the separators stay on the text baseline.
   Adding `padding-inline` also widens the horizontal target, which is the axis breadcrumbs
   actually fail on.
3. **Update the explanatory comment** at `packages/components/src/components.css:101-108` to
   name the new members and why each took the strategy it did. That comment is the reason this
   block is maintainable; leaving it stale is how the next control gets missed.
4. **Do not touch `[data-bn="tag-remove"]`'s `width: 1rem; height: 1rem`** at
   `packages/components/src/components.css:1235-1236`. See Notes — it is already compliant and
   the small visible box is deliberate.
5. **Check the two remaining uncovered members of the reset group**: `dialog-close` and
   `drawer-close` (`packages/components/src/components.css:89-90`) are the same glyph-box shape
   as `alert-dismiss` and are in neither target-size rule. Measure them and, if they fail, add
   them to step 1's selector in the same pass. `command-item` and `dropdown-item` are text rows
   and are almost certainly already tall enough — measure rather than assume.

## How we will know it worked

Assert the stylesheet contract in `packages/components/src/components.test.js`. This is not a
proxy for once: the fix *is* a stylesheet change, and the token is the mechanism.

```js
const css = readFileSync(new URL('./components.css', import.meta.url), 'utf8');
for (const token of ['alert-dismiss', 'breadcrumb-item"] a']) {
  // each must resolve a 24px floor from the shared token
}
// the strongest form: every member of the button-reset :where() group must appear
// in one of the minimum-target rules
const reset = css.match(/:where\(([^)]*)\)\s*\{\s*appearance: none/)[1];
const members = [...reset.matchAll(/data-bn="([^"]+)"/g)].map((m) => m[1]);
const targetBlock = css.slice(css.indexOf('Minimum target size'), css.indexOf('BaseNative Component Styles'));
for (const m of members) {
  assert.ok(targetBlock.includes(`"${m}"`), `${m} has no WCAG 2.5.8 target-size floor`);
}
```

That last loop fails today for `alert-dismiss`, `dialog-close`, `drawer-close`,
`command-item` and `dropdown-item`, and keeps failing for any icon control added to the reset
group without a floor — which is the regression that produced this ticket. Decide in step 5
which of those five genuinely need the floor and either add them or add a short allowlist with
a measured reason per entry; do not weaken the assertion to a subset.

Run it with:

```bash
cd /home/dugan/Developer/github.com/DuganLabs/BaseNative/packages/components && node --test
```

Then measure by hand, because CSS contracts are not pixels: `pnpm start`, open
`/components/alert` and `/components/breadcrumb`, and in DevTools confirm each control's
computed box is ≥24×24. Check the breadcrumb in a narrow mobile viewport too — it is the one
that can regress under wrapping. `pnpm audit:axe` (`scripts/audit/axe.mjs`) is worth running
but does not reliably check 2.5.8, so it does not substitute for the measurement.

## Notes

- **The original audit's chip-remove claim does not hold on current main, and the obvious
  "fix" would be a regression.** `[data-bn="tag-remove"]` is visibly 16×16
  (`packages/components/src/components.css:1235-1236`) but its *hit area* is already 24×24 via
  an invisible centred pseudo-element at `packages/components/src/components.css:121-134`
  (`position: absolute`, `translate: -50% -50%`, `min-inline-size`/`min-block-size:
  var(--bn-target-size-min)`), enabled by `position: relative` at
  `packages/components/src/components.css:113-120`. WCAG 2.5.8 measures the target, not the
  glyph, so this passes. The comment at `packages/components/src/components.css:105-108`
  states the reasoning: the chip is a compact pill, so growing the real box would visibly
  change the control. Deleting `width: 1rem; height: 1rem` would enlarge every chip for no
  accessibility gain. Verify the `::before` is not `pointer-events: none` before trusting
  this — it is not, as of this writing.
- BN-018 covers the fact that the chip remove has no behaviour at all — no `initMultiselect`
  exists (`grep -rn 'export function init' packages/components/src/` returns only `initTabs`,
  `initCalendarDragDrop`, `initPipelineDragDrop`). A correctly sized button with no listener
  is still broken; that is BN-018's problem, not this one.
- Commit `84900fd` is the control-family pass that created the asymmetry this ticket closes:
  it gave the seven real controls a shared `--bn-control-height`
  (`packages/components/src/components.css:39-49`) and the icon controls only a
  border/background reset (`packages/components/src/components.css:84-99`). The target-size
  block at 101-134 was the follow-up that caught up four of them. This ticket catches up the
  rest.
- **Specificity trap, stated in the codebase's own words.** The comment at
  `packages/components/src/components.css:150-155` explains that re-declaring a property after
  the shared control group silently defeats the token the group applied. The same applies here:
  `:where()` has zero specificity, and a component's own rule (e.g. `[data-bn="alert-dismiss"]`
  at line 445) comes later in the file and wins unconditionally. So step 1 must add the
  `display: inline-flex` to the rule at 445 itself, not to the `:where()` group, or it will not
  take effect.
- Changing `packages/components/src/components.css` needs a changeset. CLAUDE.md marks
  `.changeset/*` orchestrator-only for subagents — report it upward rather than writing one.
