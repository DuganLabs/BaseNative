# Proposal — design-system codes in the `@basenative/validate` taxonomy

**Status: proposal. Nothing here is implemented.** No file under `packages/validate/`
is touched by the branch that adds this document. `packages/validate/src/codes.js` is on
the validator's critical path — every consumer of `validateTemplate()` sees whatever
lands there — so the taxonomy is for review before any code exists.

**What it would change.** Today a design-system mistake is caught, if at all, by a model
reading a diff and noticing. That is the least reliable instrument available: it degrades
under context pressure, it is not reproducible, and it cannot be run in CI. Every code
below moves one class of mistake to parse time, where it is a structured object with a
span, a message and a concrete corrected string — the same contract every existing
`BN_E_*` code already meets.

---

## The rule every code here has to satisfy

From `packages/validate/src/codes.js`, unchanged and not up for negotiation:

> every diagnostic must be repairable by a model from the object alone, with no access to
> documentation. If a model would have to look something up to act on a diagnostic, that
> diagnostic is incomplete.

This is why each proposal below carries an example `suggestion` that is **corrected
syntax**, not advice. `"use a design token"` fails the rule. `data-variant="default"` —
naming the value, in the markup the author wrote — passes it.

It also bounds what can be proposed. Three otherwise-attractive rules are excluded at the
bottom of this document precisely because their fix is not derivable from the error.

---

## The data dependency, and the ordering it forces

Five of the six codes need to know what components exist, what `data-bn` contracts they
own, and which variant values actually have a CSS rule. That is exactly
`.agents/component-index.json`, generated by `scripts/llms-txt.js` in the same pass as
`llms-full.txt` and staleness-checked in CI.

`@basenative/validate` currently has one dependency (`@basenative/runtime`) and reads no
repo-local file. Three ways to close the gap, in the order I would recommend them:

1. **Caller-supplied, default off.** `validateTemplate(src, { components })`, where
   `components` is the parsed index. No new dependency, no file I/O in the validator, and
   the design-system codes simply do not fire when the caller does not pass it. The MCP
   server, the CLI and `ds-guard` each load the index themselves.
2. **A separate entry point.** `@basenative/validate/design-system` exporting
   `validateDesignSystem(src, index)`, so the core validator's surface is untouched and
   the codes ship in the same taxonomy object.
3. **Bundled snapshot.** Ship a pruned copy of the index inside the package at publish
   time. Rejected here: it makes the validator's answers depend on its own release
   cadence rather than on the consumer's installed `@basenative/components`, which is the
   version that actually decides whether `variant="neutral"` has a rule.

**Option 1 is what the code shapes below assume.** Under it, a consumer on an older
`@basenative/components` gets answers about *their* stylesheet, which is the only correct
behaviour.

---

## The severity question — needs an owner decision

`codes.js` defines severity by renderability, not by policy:

> `ERROR` — the template will not render, or will render wrongly and silently.
> `WARNING` — renders today, but relies on behaviour that is unspecified or fragile.

and warns, at `diagnostic()`:

> The validator must never report as an error something the runtime allows.

Every design-system violation *renders*. Under a strict reading they would all be
`WARNING`. But three of them render **wrongly and silently**, which is the first clause
of `ERROR`:

- a `data-variant` with no matching rule renders with no background and no colour, and
  nothing anywhere says so (`renderBadge(…, { variant: 'neutral' })`, live in
  `GreenPut/apps/tenant-site/src/scanner.ts:47-48`);
- `var(--bn-color-surface-2, #1f1f23)` where `--bn-color-surface-2` is undeclared renders
  a hardcoded dark grey that no theme can reach — correct in one theme, invisible in the
  other;
- a hardcoded colour in a `style=""` attribute is correct in the theme it was written in
  and wrong in the other.

Severities below follow that reading. **The one place it needs a ruling** is
`BN_E_INLINE_STYLE_TOKEN`, which is split by value kind (colour → `ERROR`, length →
`WARNING`) rather than by the constitution's Axiom 2 ("Zero inline styles"), which would
make every inline style an `ERROR` regardless. Axiom 2 is a project policy; the taxonomy
is currently a renderability model. Making it enforce policy is a legitimate choice but it
is a change of meaning, not an added code, so it is the owner's call. `diagnostic()`
already supports a per-call `severity` override, so either reading is implementable
without touching the shared definitions.

## Proposed codes

Six codes. Shapes are written in the `CODES` style so the review can read them as they
would land — they are illustrative, and are **not** to be pasted into `codes.js` before
the taxonomy is signed off.

### 1. `BN_E_INLINE_STYLE_TOKEN`

A `style="…"` declaration whose literal value is one a `--bn-*` token already declares.

```js
/**
 * Inline style carrying a value a token already names. A hardcoded colour is
 * correct in exactly one theme: `background:#18181b` is invisible on a dark
 * surface and the author never sees it, which is the "renders wrongly and
 * silently" case. A hardcoded length is merely untokenised, so it downgrades.
 */
BN_E_INLINE_STYLE_TOKEN: {
  severity: ERROR,
  confidence: CONFIDENCE.HIGH,
  summary: 'Inline style value that a design token already declares',
},
```

| | |
|---|---|
| Fires on | `<div style="background:#18181b;padding:0.5rem">` |
| `message` | `style="background:#18181b" hardcodes a colour --bn-color-gray-900 is declared as, so this element cannot follow the theme` |
| `suggestion` | `style="background:var(--bn-color-gray-900);padding:var(--bn-space-2)"` |
| `severity` override | `WARNING` when every literal in the declaration is a length rather than a colour |
| Repairable alone? | Yes — the corrected attribute is the whole fix. |
| Evidence | `packages/visual-builder/src/bn-canvas.js:99,100,128` — three live sites, found by `scripts/ds-lint.js` DS007. |

The token lookup is property-scoped, the same way `scripts/ds-lint.js` does it: `1rem` is
both `--bn-font-size-base` and `--bn-space-4`, but `padding:1rem` can only mean
`--bn-space-4`. Without that scoping the suggestion is ambiguous and the code fails the
repairability rule.

### 2. `BN_E_UNKNOWN_COMPONENT`

`data-bn="…"` naming a contract no component in the index owns.

```js
/**
 * A `data-bn` contract nothing declares. The element renders as a bare tag with
 * no styling at all and no error, which reads to the author as "the design
 * system is broken" rather than "that name does not exist" — the same silent
 * class as BN_E_CONTROL_FLOW_ON_ELEMENT, in markup instead of directives.
 */
BN_E_UNKNOWN_COMPONENT: {
  severity: ERROR,
  confidence: CONFIDENCE.MEDIUM,
  summary: 'Unregistered data-bn contract',
},
```

| | |
|---|---|
| Fires on | `<span data-bn="chip">Active</span>` |
| `message` | `data-bn="chip" is not a registered BaseNative contract; no stylesheet declares a rule for it, so this element renders unstyled` |
| `suggestion` | `Did you mean data-bn="badge"? <span data-bn="badge" data-variant="default">Active</span>` |
| Repairable alone? | Yes when a near name exists; otherwise the message still names the failure exactly. |

Confidence is `MEDIUM`, not `HIGH`, for the reason the existing
`BN_E_UNKNOWN_DIRECTIVE` is: the nearest-name suggestion is a guess at intent. Reuse
`nearestName()` from `packages/validate/src/validate.js`, which already exists for
directives and scales its threshold with name length.

### 3. `BN_E_DEPRECATED_COMPONENT`

`data-bn="…"` on a contract whose owning component's JSDoc carries `@deprecated`.

```js
/**
 * Renders correctly today. The cost is that it will stop, on a schedule the
 * author cannot see from the markup — the definition of "relies on behaviour
 * that is unspecified", so WARNING rather than ERROR.
 */
BN_E_DEPRECATED_COMPONENT: {
  severity: WARNING,
  confidence: CONFIDENCE.HIGH,
  summary: 'Deprecated component',
},
```

| | |
|---|---|
| `message` | `data-bn="<old>" is deprecated: <the text after @deprecated in the component's own JSDoc>` |
| `suggestion` | `<tag data-bn="<replacement>">` — the replacement contract, taken from the same `@deprecated` line |
| Repairable alone? | Yes, **provided** `@deprecated` names a replacement. |

That proviso is the one piece of new discipline this code needs: a bare `@deprecated`
with no replacement produces a diagnostic a model cannot act on, which is the taxonomy's
one hard rule. If this code is adopted, the index generator should treat a bare
`@deprecated` as an extraction gap and say so, exactly as it already does for a
declaration it cannot bound. **No component in the repo is currently deprecated** — the
generated index reports `deprecated: false` for all 63 — so this code ships dormant and
is a forward contract rather than a fix for anything live.

### 4. `BN_E_INVALID_VARIANT`

A `data-<axis>="<value>"` on a known contract where the axis *is* styled but that value
has no rule.

```js
/**
 * The single most expensive silent failure in the design system. A data-variant
 * with no matching selector does not error and does not fall back: the element
 * renders with the base rule only, which for a badge means no background and no
 * colour. Two of these are in production right now.
 */
BN_E_INVALID_VARIANT: {
  severity: ERROR,
  confidence: CONFIDENCE.HIGH,
  summary: 'Variant value outside the component\'s declared set',
},
```

| | |
|---|---|
| Fires on | `<span data-bn="badge" data-variant="neutral">` |
| `message` | `data-variant="neutral" has no rule on data-bn="badge"; it renders with no background and no colour. Declared values: default, error, primary, success, warning` |
| `suggestion` | `<span data-bn="badge" data-variant="default">` |
| Repairable alone? | Yes — the message enumerates the whole legal set. |
| Evidence | `GreenPut/apps/tenant-site/src/scanner.ts:47,48`, live. |

Two conditions must gate it, both already modelled in `scripts/lib/css-model.js`:

- **Open sets.** `[data-bn="dropdown-menu"][data-position^="top"]` styles `top-end` and
  `top-start`. An axis carrying any `^=`/`$=`/`*=`/`~=`/`|=` rule is not a closed
  enumeration and must not fire this code. An adjacency-only matcher would have missed
  those four rules entirely and produced false positives on correct markup.
- **Presence rules.** `[data-bn="pipeline-block"][data-status]` is a documented fallback:
  23 statuses are enumerated and anything else still gets a border from
  `--bn-pipeline-status-color`. Where a presence rule exists, an unlisted value is legal.

### 5. `BN_E_INERT_VARIANT_AXIS`

A `data-<axis>` on a known contract where **no** stylesheet reads that axis for that
contract at all.

```js
/**
 * Distinct from BN_E_INVALID_VARIANT, and distinct in its fix: there is no value
 * that would work. renderCard accepts a `variant` option, escapes it into
 * data-variant, and no stylesheet has ever read it — an API promise with nothing
 * behind it, which a consumer is already relying on.
 */
BN_E_INERT_VARIANT_AXIS: {
  severity: WARNING,
  confidence: CONFIDENCE.HIGH,
  summary: 'Style axis no stylesheet reads',
},
```

| | |
|---|---|
| Fires on | `<article data-bn="card" data-variant="highlight">` |
| `message` | `data-variant is not read by any rule for data-bn="card" — no value of it changes rendering` |
| `suggestion` | `<article data-bn="card">` — remove the attribute, or add a `[data-bn="card"][data-variant="highlight"]` rule to packages/components/src/components.css |
| Repairable alone? | Yes — deleting the attribute is always safe, since by construction it does nothing. |
| Evidence | `packages/components/src/card.js`, plus `renderTreeGrid`'s `data-level` (styled on `tree-item`, never on `treegrid-row`). Both are in `.agents/component-index.json` under `inertAxes`. |

`WARNING`, not `ERROR`: the author gets what the base rule renders, which is a coherent
card. They do not get what they asked for, but nothing is broken on screen.

### 6. `BN_E_UNDECLARED_TOKEN`

`var(--bn-…)` in template CSS naming a custom property nothing declares.

```js
/**
 * The fallback becomes the permanent value and the var() wrapper is decoration.
 * Renders — in exactly one theme, forever, with no signal that theming was
 * silently opted out of.
 */
BN_E_UNDECLARED_TOKEN: {
  severity: ERROR,
  confidence: CONFIDENCE.HIGH,
  summary: 'Reference to an undeclared --bn-* token',
},
```

| | |
|---|---|
| Fires on | `<div style="background:var(--bn-color-surface-2,#1f1f23)">` |
| `message` | `--bn-color-surface-2 is not declared by any BaseNative stylesheet, so #1f1f23 is the only value this will ever have and the element cannot be themed` |
| `suggestion` | `Declare --bn-color-surface-2: #1f1f23 in packages/components/src/tokens.css, or write background:#1f1f23 to admit it is a literal` |
| Repairable alone? | Yes — both branches are spelled out and either one resolves it. |
| Evidence | `packages/builder/src/builder.css` references **10 undeclared `--bn-*` names across 19 sites** (`scripts/ds-lint.js` DS006): the nine `--bn-color-*` the audit found, plus `--bn-font-family-mono` at line 142, which the audit missed because it scoped its grep to `--bn-color-*`. |

Scoped to the `--bn-` prefix on purpose. `--cb-*` (23 declarations in
`packages/combobox/src/styles.css`) and `--kb-*` (32 in `packages/keyboard/src/styles.css`)
are package-local namespaces, and a consumer's own `--app-accent` is none of the
validator's business.

## Summary

| Code | Severity | Confidence | Catches | Live instances |
|---|---|---|---|---:|
| `BN_E_INLINE_STYLE_TOKEN` | ERROR / WARNING | high | inline style where a token exists | 3 |
| `BN_E_UNKNOWN_COMPONENT` | ERROR | medium | unregistered `data-bn` contract | 0 in-repo |
| `BN_E_DEPRECATED_COMPONENT` | WARNING | high | deprecated component | 0 (dormant) |
| `BN_E_INVALID_VARIANT` | ERROR | high | variant outside the declared set | 2 (consumer) |
| `BN_E_INERT_VARIANT_AXIS` | WARNING | high | axis no stylesheet reads | 2 |
| `BN_E_UNDECLARED_TOKEN` | ERROR | high | `var(--bn-…)` with no declaration | 19 |

"Live instances" counts what exists today, from `scripts/ds-lint.js` and
`.agents/component-index.json`. Two of the six would fire zero times on the current tree
— they are there to stop a class of mistake, not to describe one.

---

## Deliberately not proposed

Each of these fails the repairability rule, and adding them would weaken it for every
existing code.

- **`BN_E_HAND_ROLLED_COMPONENT`** — markup reproducing a component's contract by hand
  instead of calling its renderer (`DuganLabs/worker/index.js` and `pages/js/ecosystem.js`
  both hand-write `renderPackageCard`'s markup). Tempting, and the component index already
  carries the `useInsteadOf` line it would need. But `validateTemplate()` sees a template
  string with no idea whether it *is* a renderer's output: `renderBadge`'s own body would
  fire this code against itself. Detecting it needs the call graph, which is
  `scripts/component-usage.js`'s job, not a parser's.
- **Variant-ceiling breaches** — enforced by `scripts/ds-lint.js` against the whole
  stylesheet, because a ceiling is a property of the CSS, not of any one template. A
  parser looking at one element cannot see that an axis has 23 values.
- **"Prefer this component over raw markup"** — `<div class="card">` is not wrong; it is
  differently styled. A code that fired on it would produce a suggestion the validator
  cannot know is correct, which is guessing at intent.

---

## For the owner to decide before any of this is written

1. **Delivery**: option 1 (caller-supplied index), 2 (separate entry point) or 3 (bundled
   snapshot). The code shapes above assume 1.
2. **`BN_E_INLINE_STYLE_TOKEN` severity**: keep the renderability model (colour = ERROR,
   length = WARNING), or enforce Axiom 2 and make every inline style an ERROR.
3. **`@deprecated` discipline**: require a named replacement, and treat a bare
   `@deprecated` as an extraction gap in the component index.
4. **Whether `BN_E_INERT_VARIANT_AXIS` should instead be fixed at the source** — deleting
   `renderCard`'s inert `data-variant` and `renderTreeGrid`'s `data-level` removes both
   live instances, at which point the code guards against reintroduction rather than
   reporting current state.
